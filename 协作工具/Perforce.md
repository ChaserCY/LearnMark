# 为什么选择Perforce:
1. 以==资源文件==为==主要工作对象==的开发流程。虚幻项目的文件是二进制格式，不支持并行编辑
2. ==集成性==。在虚幻编辑器中，对于资源的工作流程基本上都是遵循了Perforce的流程。
3. ==大型文件管理能力==。在游戏开发过程中，我们常常会涉及很多体积较大的文件，有些文件甚至以GB为单位。

# 开发特殊区分
## 流式与分支式开发模式
### 1. 传统 Branch（右图）

==分支只是独立文件夹副本，**没有系统定义上下游**。==
传统分支只是**独立的代码副本**：

- 分支之间**没有预设关系**，只是一堆平行的代码拷贝
- 合并、基线同步全靠人手动写命令，自己记住谁合并到谁
- 你可以随便创建分支，没有层级约束；很容易搞乱合并方向（比如把 release 代码误合并回开发分支）
- 分支只是单纯目录拷贝，**不知道这个分支是开发分支还是发布分支**，没有角色定义
- 适合小团队；大项目容易出现合并混乱、漏合并、方向搞反

一句话痛点：**规则靠人，人会忘、会点错**

### 2. Stream 流式（左图，Perforce Streams）

Stream 是**带角色和层级关系的分支模型**，它把分支定义成一套有向的数据流：

- 每个 Stream 自带类型：`main`主干、`dev`开发流、`rel`发布流，**预先定义好上下游父子关系**
    
    图里：`main`是根，下面分出 dev2.1/dev2.2/dev2.3；上面分出 rel2.1/rel2.2/rel2.3
- **合并方向被系统约束**：只能按定义好的流向合并（dev → main → rel），防止反向错误合并
- 系统自动感知基线、自动计算哪些变更该合并，不用人维护复杂的分支映射
- 流自带语义：系统知道这个流是用来开发还是发布，强制规范团队工作流
- 本质上底层还是分支，但**增加了元数据来管理分支之间的数据流**

一句话优势：**规则写在系统里，工具帮你管住合并方向**。

## 集中式与分布式
### **集中式：==只有一台中央服务器==存完整仓库；本地电脑只存当前文件 + 部分历史。**

### **分布式：每一台开发者电脑，都完整==克隆==一份仓库（全部历史、所有分支）。**

## 锁机制（二进制资产重点，游戏美术 / 模型）

两种模式：

1. ==**默认==：多人可同时 checkout（并行编辑，适合==代码文本==）**
    
    - 多个人可以同时`p4 edit`同一个文件；提交时遇到冲突需要手动 resolve 合并。
    
2. ==**独占锁== +l（==二进制文件==，贴图、模型、UE 资产）**
    
    文件类型带`+l`，一旦你 checkout+lock：**别人不能再打开这个文件 edit**，直到你 submit 或者 revert 放弃修改。
    
    > 游戏项目里美术资源基本开独占锁，二进制没法合并，防止两个人改同一张贴图互相覆盖。

## 总结
- **SVN：集中式 + 传统目录分支**
- **P4：集中式 + 传统 Branch / Stream 流分支**（P4 的 Stream 是 P4 自己在集中式之上增加的分支流向规则，和分布式无关）
- **Git：分布式 + 轻量分支模型**
