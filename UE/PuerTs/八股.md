# 一、 核心架构与绑定原理篇

### Q1：Puerts 底层是怎么跑起来的？它的 JS/TS 虚拟机选型是怎样的？

- **核心考察点**：虚拟机选型与平台兼容性。
    
- **标准回答**：
    
    1. **执行引擎**：Puerts 默认基于 **Google V8 引擎**（也可选轻量级 **QuickJS** 或集成 **Node.js** 运行环境）。
        
    2. **平台差异与限制**：
        
        - **PC / Android**：可以直接开启 V8 的 ==**JIT（即时编译）**==，性能极为强悍。
            
        - **iOS**：由于苹果安全沙盒禁止分配可执行内存页（W^X 机制），V8 无法使用 JIT，只能运行在 **JIT-less（解释器模式/Ignition）**，或者替换为 QuickJS 降低包体和内存。
            
    3. **生命周期宿主**：在 UE 中通常作为 ==GameInstanceSubsystem== 或挂载于引擎主循环中，==随 GameInstance 的生命周期创建和销毁== v8::Isolate（独立的虚拟机实例）。
        

---

### Q2：Puerts 的 C++ 与 TS 互相调用，底层是怎么实现的？（反射绑定 vs 静态绑定）

- **核心考察点**：==跨语言互操作实现方式与底层反射==。
    
- **标准回答**：  
    Puerts 提供了两种互操作桥梁：
    
    1. ==**动态反射绑定==（基于 UE 反射系统，开箱即用）**：
        
        - **原理**：Puerts 借助 UE 的 UClass、UFunction、FProperty 反射元数据。
            
        - 当 TS 访问 UE.Class.Load 或调用某个 UFunction 时，底层通过 UFunction::Invoke 或 ProcessEvent 解析参数栈并动态派发。
        - `UObject::ProcessEvent`：最底层、最常用；**参数放在一块连续内存结构体**；逆向 / 热更 / Puerts 常用；
		- `UFunction::Invoke`：高层封装，参数分开传，内部最终也会走到 ProcessEvent。
            
        - **优缺点**：无须提前生成代码，灵活度高，但每次调用有反射查表和装箱拆箱开销。
            
    2. ==**静态绑定==（Static Binding，极致性能）**：
        
        - **原理**：利用 C++ 模版元编程或提前代码生成工具，直接把 C++ 函数指针/类成员指针包装成 V8 的 v8::FunctionCallback，注入到 V8 的原型链（Prototype）中。
            
        - **优缺点**：调用时直接通过 C++ 函数指针跳转，**完全绕过 UE 的 ProcessEvent 反射系统**，性能接近原生 C++ 调用，适合高频数学计算或物理 API。

### Q3：参数跨语言传递时，值类型（Struct）与引用类型（UObject）底层如何包装？

- **核心考察点**：==内存封包、装箱拆箱==（Boxing/Unboxing）。
    
- **标准回答**：
    
    - ==**UObject 引用类型**==：
        
        - V8 端会创建一个 v8::Object（包装对象），其内部藏有一个隐藏指针（InternalField），存储原生 UObject* 的内存地址。
            
    - ==**值类型==（如 FVector, FRotator 等 UScriptStruct）**：
        
        - **只读/临时引用**：直接==将原生内存指针封包==，避免深拷贝。
            
        - **按值传递/JS 本地创建**：Puerts 会在 ==C++ 原生堆上分配一段内存==存储该结构体数据，并在 V8 对象析构时（通过弱回调）释放该段内存。

### Q4：Puerts 的 mixin 底层做了什么？为什么说它是“侵入式”的？

- **核心考察点**：运行时类混入原理。
    
- **标准回答**：
    
    - **底层行为**：当调用 blueprint.mixin(UClass, TsClass) 时，Puerts 会遍历 TS 类的原型链：
        
        1. 如果在目标 UClass 中==**已存在**对应名字的 UFunction==（如 ReceiveBeginPlay），Puerts 会修改该 UFunction 的==调用入口函数==（Func 指针），将其==重定向==到 Puerts 的通用派发器（Dispatcher）。
            
        2. 如果目标类中**不存在**该函数，Puerts 会在运行时==利用 UE 反射 API **动态创建并注册一个 UFunction 对象**==，==强行挂进该 UClass 的 Children 链表和 FuncMap 反射哈希表中。==
            
    - **设计影响**：由于它直接篡改了目标 UClass 的内部结构，属于运行时元编程（Metaprogramming），==混入原生类时极易破坏内存假设==（详见后文 GC 踩坑题）。

# 二、 双 GC 架构与生命周期死局篇（面试必杀题）

### Q5：V8 GC 与 UE GC 是如何协同工作的？如何防止对象悬空与野指针？

- **核心考察点**：==跨虚拟机双重内存管理的解耦机制==。
    
- **标准回答**：
    
    - **各自的机制**：
        
        - **UE**：以 RootSet 为起点，通过 UPROPERTY() 进行==遍历标记的 **Mark-Sweep GC**。(标记清扫)==
            
        - **V8**：基于新生代/老生代的==分代式垃圾回收==。
            
    - **协同桥梁（Weak Callback）**：
        
        - 当在 TS 中持有一个 UObject 时，V8 的包装对象会通过 v8::Persistent ==持有底层引用。==
            
        - **防止原生对象被 UE 误删**：根据 objectTakeByNative 的策略，如果不归原生管理，Puerts 会为该 UObject 挂载一个引用保证存活；
            
        - **防止原生对象被引擎删后 TS 访问野指针**：Puerts 内部用 TWeakObjectPtr\<UObject> 或==监听== UE 的 GUObjectArray ==对象销毁回调==。一旦引擎端调用了 Destroy()，内部指针清空，TS 端再次调用会抛出 ==Invalid Object 异常==，而不会直接访问野指针引发崩溃。
            
        - **反向释放**：当 TS 端==不再引用==该对象且==被 V8 回收==时，==V8 会触发 MakeWeak 设置的弱引用回调==，==通知 C++ 端解绑原生映射关系==，释放中间胶水层内存。

### Q6：你在项目中遇到过最隐蔽的 Puerts 崩溃是什么？怎么解决的？

- **核心考察点**：项目实战踩坑深度，能否把“理论机制”转化为“排错能力”（**直接把你前面的真实排错经历拿来作答，极具说服力！**）。
    
- **高分回答模板**：
    
    > “遇到过最隐蔽的问题是：**编辑器下运行完美，但一打出独立包启动立刻触发 Fatal Error(致命) 崩溃**：  
    > Fatal error: Encountered 1 object(s) breaking Disregard for GC assumptions。
    > 
    > **排查过程**：
    > 
    > 1. 日志虽然报在 VerifyGCAssumptions，但在崩溃前的 Warning 中捕捉到了关键信息：  
    >     Disregard for GC object None referencing Function ... BasePlayerController:ReceiveBeginPlay which is not part of root set。
    >     
    > 2. **原因剖析**：  
    >     UE 打包版本中存在常驻内存优化池（Disregard for GC）。原生 C++ 模块（Native Class）在引擎早期初始化时就会被锁入常驻池，引擎假设其结构**不可变**。  
    >     当时我们在 TS 中直接使用了 @mixin 去混入原生 C++ 类 ABasePlayerController。Puerts 底层为 TS 方法动态生成了一个普通（非 Root）的 UFunction，导致**常驻池里的 Native Class 引用了需要常规 GC 的动态对象**，启动时直接破坏了 GC 假设，被引擎断言拦截。
    >     
    > 3. **解决方案**：  
    >     颠倒设计关系——C++ 基类只做接口定义（声明 BlueprintNativeEvent），派生出一个空白蓝图，TS 的 mixin **直接挂在蓝图生成的类（\_C）上**。由于==蓝图资产不属于 Native 常驻池==，既优雅==避免了 GC 校验崩溃==，又==避免了混入 C++ 原生类带来的全局污染。==”
    >

# 三、 性能调优与工程化落地篇

### Q7：Puerts 中高频调用的性能损耗主要在哪里？如何进行优化？

- **核心考察点**：==性能瓶颈意识与调优手段==。
    
- **标准回答**：
    
    1. **主要损耗瓶颈**：
        
        - ==**跨语言边界开销==（Crossing Boundary）**：V8 上下文切换进入 C++ 原生函数的上下文切换成本。
            
        - ==**反射派发开销**==：UFunction::ProcessEvent 查找与动态参数栈解包。
            
        - **==频繁的数据封包与内存拷贝==**：比如每帧在 TS 和 C++ 之间频繁传递 FVector、大体积 TArray。
            
    2. **调优方案**：
        
        - ==**核心计算留在原生层**==：Tick、复杂数学向量矩阵运算、大型物理检测坚决留在 C++，TS 只处理状态流转与业务逻辑。
            
        - ==**使用静态绑定==（Static Binding）**：对于必须由 TS 频繁调用的底层 API，利用 Puerts 的声明生成工具做静态绑定，绕过反射。
            
        - **==避免在循环中传递容器==**：尽量不要在 TS 里把一个巨大的 TArray 逐个元素传给 C++，应设计批量接口，或通过共享内存/Buffer 处理。
            
        - ==**减少字符串传递**==：使用 FName 或提前缓存的 GameplayTag，避免大量高频的原生 FString 转 JS 字符串造成的堆内存分配。

### Q8：Puerts 的代码热重载（Hot Reload）底层原理是怎样的？

- **核心考察点**：==TS 热更新机制==。
    
- **标准回答**：
    
    - ==TS 编译后输出标准的 CommonJS 或 ES6 模块==。
        
    - **热重载==流程**==：
        
        1. 清除 V8 虚拟机内部的模块缓存（require.cache）。
            
        2. 重新执行新模块的 JS 文件，获取新的类或原型函数。
            
        3. 如果使用了 mixin，Puerts 会更新 UClass 内部之前绑定的 UFunction 派发指针，将其执行链指向新生成的 JS 函数对象。
            
        4. 此时场景中已经实例化的蓝图/Actor 无须重启，下一帧调用时就会直接跳转执行新的脚本代码。

### Q9：多线程场景下能不能直接在子线程调用 TS 代码？为什么？

- **核心考察点**：==V8 线程模型限制==。
    
- **标准回答**：
    
    - **绝对不能直接调用**。
        
    - **原因**：一个 v8::Isolate 实例是==**严格单线程**==的。如果 UE 的==异步任务线程==（如 TaskGraph 或异步加载线程）并发访问同一个 V8 实例，会直接==引发数据竞争崩溃==。
        
    - **正确做法**：如果 C++ 子线程产生数据需要通知 TS，必须通过==任务派发机制==（如 AsyncTask(ENamedThreads::GameThread, ...)）==将回调调度回**游戏主线程==（GameThread）**，==再由主线程安全地触发 TS 的回调函数==。

# 四、 方案横向选型对比篇（技术视野）

### Q10：在 UE 项目中，为什么选择 Puerts（TypeScript）而不是 Lua（如 UnLua / Slua）？

- **核心考察点**：技术选型思考、优劣势评估。
    
- **横向对比总结表**：
    

|           |                           |                                   |                                                    |
| --------- | ------------------------- | --------------------------------- | -------------------------------------------------- |
| 维度        | Puerts (TypeScript)       | UnLua / Slua (Lua)                | 面试分析与评价                                            |
| **类型安全**  | **极高（编译期强类型检测）**          | 较弱（动态弱类型，依赖运行时）                   | 适合中大型团队协作，TS 重构代码风险极低，IDE 跳转与补全体验拉满。               |
| **语言生态**  | **庞大（Node.js / npm）**     | 相对封闭（主要是游戏内脚本库）                   | 可以无缝借助前端成熟工具链进行代码分析、打包、CI/CD 构建。                   |
| **执行性能**  | **PC/安卓 JIT 极快**；iOS 解释执行 | **LuaJIT 极快**；iOS 下普通 Lua VM 性能较稳 | PC 和安卓端 V8 性能吊打普通 Lua；但 iOS 端由于不能开启 JIT，纯算力两者差异不大。 |
| **虚拟机开销** | 内存与包体占用相对较大（V8 较重）        | **极小（Lua VM 极其轻巧）**               | 极度苛刻包体和低端小游戏更偏向 Lua；重型中重度项目 TS 优势更明显。              |
| **团队复用**  | 前端开发、服务端 TS 人员无缝上手        | 需要专门熟悉 Lua 游戏脚本生态                 | 大大降低招人和前后端技术栈统一的学习成本。                              |
