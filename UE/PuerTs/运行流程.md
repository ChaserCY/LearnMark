### 阶段 1：引擎初期启动与 Puerts 插件加载（Plugin Startup）

> **时机**：引擎启动，加载 .uplugin 插件模块（FEngineLoop::PreInit）

1. **加载 Puerts 模块**：  
    UE 启动时根据 Puerts.uplugin 里的 LoadingPhase: PreDefault，加载 Puerts 的 C++ 动态库。
    
2. **初始化 V8 引擎底座**：  
    执行 FPuertsModule::StartupModule()。此时 Puerts 会在全局初始化 **V8 引擎平台（v8::Platform）** 和 V8 初始 Flags。
    
3. **注册静态 C++ 反射**：  
    Puerts 通过宏（如 PUERTS_MODULE）收集你手动导出的原生 C++ 类和方法，建立类型索引。
    

- ⚠️ **注意**：在这个阶段，**V8 的具体执行上下文（JsEnv 虚拟机）还没有被创建！** 此时只是“搭建好了 V8 基础框架”。
    

---

### 阶段 2：资产加载与 CDO 创建（Asset Loading & CDO Phase）

> **时机**：引擎打开地图/打开蓝图编辑器/启动编辑器时加载资产

1. **反序列化蓝图资产**：  
    UE 从磁盘读取 .uasset（如 BP_PlayerController），并使用 Kismet 编译器构建蓝图。
    
2. **创建 CDO（Class Default Object 类默认对象）**：  
    UE 会为 BP_PlayerController 创建一个 CDO 内存实例。
    
3. **触发构造/加载生命周期**：  
    ==依次触发 C++ 构造函数 →→PostLoad()→→ **蓝图的 Construction Script（构造脚本）**==。

- 💥 **崩溃高发区（划重点）**：  
    在**编辑器启动阶段**打开蓝图资产时，系统走到这里，而**阶段 3 的 JsEnv 根本还没创建**。如果你在构造脚本或 C++ 构造函数里尝试获取 JsEnv 或调用 TS 代码，就会直接拿到 nullptr 暴毙！
    
---

### 阶段 3：虚拟机实例化与 TS 脚本加载（JsEnv Setup Phase）

> **时机**：点击 PIE 运行游戏，或 GameInstance::Init / Subsystem::Initialize 触发时

当你真正进入游戏运行环境时，Puerts 才会真正启动 TS 环境：

1. **实例化 FJsEnv**：  
    C++ 执行 std::make_shared<puerts::FJsEnv>()。
    
2. **创建 V8 Isolate 与 Context**：  
    在内存中开辟独立的 V8 内存空间（Isolate）和上下文（Context）。
    
3. **注入全局环境**：
    
    - 注入 global、console.log（重定向到 UE 的 UE_LOG）。
        
    - 注入 require / import 模块加载器，指向项目下的 Content/JavaScript 目录。
        
    - **绑定 UE 反射系统**：将 UE 的 UClass、UFunction、UProperty 动态映射为 V8 的 FunctionTemplate 和 ObjectTemplate，让 JS 能看到 UE.APlayerController 等类型。
        
4. **执行 TS 入口文件**：  
    读取并运行编译后的入口文件（如 JavaScript/Index.js）。
    

---

### 阶段 4：动态注入与 Mixin 挂钩（Dynamic Mixin Phase）

> **时机**：入口 TS 脚本被执行，调用 puerts.mixin 或绑定逻辑时

当 TS 代码执行到 puerts.mixin(UE.BP_PlayerController, JSPlayerController) 时：

1. **查找内存中的 UClass**：  
    Puerts 在 UE 的 GUObjectArray 中找到 BP_PlayerController 的 UClass 指针。
    
2. **劫持/重定向函数调用（ProcessEvent Hook）**：
    
    - Puerts 会修改这个 UClass 的 ProcessEvent（UE 反射调用的核心入口）或覆盖特定的 UFunction::NativeFunc。
        
    - 将该函数的回调入口改指向 Puerts 的 FFunctionTranslator::Call。
        
3. **扩展内存布局**：  
    如果在 TS 中写了新的 @uproperty() 属性或方法，Puerts 会动态向该 UClass 补充 UFunction / FProperty 元数据。
    

- 💡 **结果**：此时，UE 引擎以为 BP_PlayerController 还是那个普通的蓝图，但实际上它的**核心函数指针已经被替换成了指向 V8 引擎的桥接器**。
    

---

### 阶段 5：Gameplay 运行时交互与 GC 同步（Runtime & GC Phase）

> **时机**：游戏正式运行（BeginPlay、Tick、玩家输入）

1. **事件触发与转接流程**：
    
    - **UE 侧**：游戏生成 BP_PlayerController 实例，调用 BeginPlay()。
        
    - **引擎反射**：UE 调用 ProcessEvent(BeginPlay)。
        
    - **Puerts 拦截**：由于阶段 4 挂了 Hook，ProcessEvent 被转接到 Puerts 的 C++ 桥接代码。
        
    - **V8 执行**：Puerts 将 UE 参数包装为 V8 JS 对象，进入 V8 虚拟机，执行 TS 中的 ReceiveBeginPlay()。
        
    - **结果返回**：TS 执行完毕，Puerts 把返回值打包回 UE 的内存结构中。
        
2. **跨语言垃圾回收（GC 同步）**：
    
    - **UE GC**：依靠 UObject 的引用计数和垃圾回收。
        
    - **V8 GC**：依靠 V8 的标记清除（Mark-Sweep）算法。
        
    - **Puerts 桥梁**：Puerts 实现了 FGCObject 接口。当 JS 持有一个 UE 对象（如 this.targetActor）时，Puerts 会在 C++ 侧用 v8::Persistent + AddToRoot() 防止 UE 把这个 Actor 提前删掉；当 JS 对象解绑，Puerts 释放引用，允许 UE GC 回收。
        
---

### 阶段 6：游戏结束与虚拟机销毁（Engine Shutdown）

> **时机**：退出 PIE、关闭游戏或 GameInstance 销毁时

1. **清理生命周期**：  
    触发 GameInstance::Shutdown()。
    
2. **销毁 JsEnv**：
    
    - 触发 V8 的垃圾回收（GC），强制释放所有 JS 侧占用的内存。
        
    - 清理所有绑定在 UClass 上的 Hook 钩子。
        
    - 销毁 V8 Context 和 Isolate。
        
3. **恢复引擎状态**：  
    UE 恢复为纯原生的 C++ / 蓝图运行状态。
    
---

### 总结：
#### 崩溃根源的时序对照表

|               |                               |                                   |                                         |
| ------------- | ----------------------------- | --------------------------------- | --------------------------------------- |
| 阶段_           | UE 引擎在做什么                     | Puerts 处于什么状态                     | 导致你崩溃的根本原因                              |
| **阶段1**       | 加载 Puerts 插件                  | V8 引擎底座就绪，**虚拟机不存在**              | -                                       |
| **阶段 2     ** | **打开蓝图编辑器，创建 CDO，运行构造脚本**     | **虚拟机不存在     (JsEnv == nullptr)** | 💥 **蓝图在构造期去找 JS 逻辑，拿到空指针崩溃！**          |
| **阶段 3**      | 点击 Play 运行游戏，GameInstance 初始化 | **启动 JsEnv 虚拟机，加载 TS**            | -                                       |
| **阶段 4**      | 游戏初始化中                        | **通过 Mixin 修改蓝图类**                | 💥 **直接 Mixin 资产蓝图导致阶段 2 的 CDO 反序列化损坏** |
| **阶段 5**      | 执行 BeginPlay / Tick           | TS 逻辑正常运行                         | -                                       |
####  核心类生命周期流转对照表

为了让你一目了然，这里总结了所有类在 **Puerts 注入后的时间线流转**：

|   |   |   |   |   |
|---|---|---|---|---|
|常见类 (Class)|阶段二：CDO 创建时机|阶段三/五：运行时实例生成|Puerts TS 逻辑最佳注入点|阶段二（CDO期）绝对禁区|
|**UGameInstance**|打开项目 / 引擎启动|点击 Play (PIE) / 启动游戏客户端|**Init() （在此创建 JsEnv）**|构造函数 / Construction Script|
|**AGameModeBase**|加载地图 / 打开 GameMode 蓝图|World 初始化 (InitializeActors)|InitGame() / BeginPlay()|构造函数 / 关联的 TS 静态调用|
|**APlayerController**|**打开 BP_PlayerController 资产**|玩家 Login / Spawn|**BeginPlay() / Input Binding**|**Construction Script 中调 TS**|
|**ACharacter**|打开角色蓝图 / 载入关卡摆放物|SpawnActor / 玩家 Possess|PossessedBy() / BeginPlay()|构造函数中读取 TS 属性|
|**UActorComponent**|加载宿主 Actor 蓝图|宿主 Actor Spawn 时|InitializeComponent() / BeginPlay()|组件构造函数|
|**UUserWidget**|打开 Widget 蓝图|CreateWidget 动态创建|Construct (UI 构建完成时)|预构造函数 (PreConstruct) 调 TS|

####  什么时候【不会】生成 CDO？

如果这个蓝图只是孤零零地躺在 Content 文件夹里，并且：

1. **没有任何关卡**摆放它。
    
2. **没有任何其他蓝图/C++** 引用它（没有 Hard Reference，硬，打包时也是）。
    
3. **项目设置（Project Settings）** 里没有填它。
    
4. **你没有在编辑器里去双击打开它**。
	
5. 父类C++没有被编译
