### 一、 函数与重写机制（Functions & Override）

在 C++ 和蓝图中存在多种函数声明方式，Puerts 对它们的重写（Override）和调用规则截然不同：

|                                 |                                        |                                       |                                                     |
| ------------------------------- | -------------------------------------- | ------------------------------------- | --------------------------------------------------- |
| 函数类型                            | 声明方式                                   | 蓝图中的表现                                | Puerts/TS 的重写（Override）行为                           |
| **C++ 普通函数**                    | void Func() (未加 UFUNCTION)             | 蓝图看不到                                 | 无法用 TS 重写；需要在 C++ 中手动用 Puerts API 绑定导出。             |
| **BlueprintCallable**           | UFUNCTION(BlueprintCallable)           | 蓝图可直接拖出节点调用                           | **TS 可以直接调用**；如果在 C++ 类上 mixin 可以重写它。               |
| **BlueprintNativeEvent**        | UFUNCTION(BlueprintNativeEvent)        | 蓝图可右键重写 (_Implementation)             | **TS 重写的绝佳对象**。TS 重写后，C++ 调用该函数会自动路由到 TS。           |
| **BlueprintImplementableEvent** | UFUNCTION(BlueprintImplementableEvent) | C++ 无实现，由蓝图实现，==注意⚠️千万不要是有参数的引擎回调函数== | **TS 可以直接重写**，相当于把蓝图事件用 TS 代替。                      |
| **蓝图自定义函数**                     | 在蓝图编辑器左侧【+函数】新建                        | 在蓝图资产内生成 Kismet 字节码                   | ❌ **绝对不要用 TS 去 mixin 重写！**（就是你刚才遇到的 .uasset 序列化崩溃）。 |

> **核心混淆点**：开发者容易把“蓝图编辑器里新建的函数”和“C++ 里的 UFUNCTION”混为一谈。**Puerts 的 mixin 最擅长且最安全重写的是 C++ 的 BlueprintNativeEvent**，而不是蓝图资产内部自己建的函数。

---

### 二、 Mixin 目标的混淆（C++ 类 vs 蓝图资产）<错>

这是 Puerts 初学者最常犯的错误：

- **混淆点**：UE.MyPlayerController (C++ 类) 与 UE.BP_PlayerController (蓝图资产) 看起来都是“类”。
    
- **Puerts 视角下的本质区别**：
    
    - **Mixin C++ 类 (UE.MyPlayerController)**：修改的是动态库（.dll / .so）加载进内存后的 UClass 结构，**绝不修改硬盘上的任何资产文件**，安全系数 100%。
        
    - **Mixin 蓝图资产 (UE.BP_PlayerController)**：修改的是内存中的 UBlueprintGeneratedClass。如果你在编辑器里点了保存（Ctrl+S），**当前内存里的临时 Hook 指针会被打包写进硬盘的 .uasset 二进制文件**，导致资产永久污染，重启编辑器时加载即崩溃！
        
---

### 三、 值类型（Struct）与引用类型（UObject）的传值混淆

C++ 和蓝图对结构体（FVector / FRotator / 自定义 USTRUCT）的处理，在传给 TS 后极易产生误解：

1. **结构体是“值拷贝（Copy by Value）”**：
    - 在 TS 中写：
```
let loc = actor.K2_GetActorLocation(); // 返回一个 FVector
loc.X = 1000; // ❌ 错误误区：以为这会改变 Actor 的位置
```
    
- **真相**：loc 只是从 C++ 拷贝到 JS 内存中的一个**结构体副本**。修改 loc.X 没有任何用，你必须显式调用 actor.K2_SetActorLocation(loc, ...)。
        
2. **UObject 指针的生命周期（GC 陷阱）**：
    
    - 如果你在 C++ 中 DestroyActor() 销毁了一个 Actor，但在 TS 中还保留着这个 actor 变量：
```
// 如果 Actor 在 C++ 侧被销毁了：
if (actor.IsValid()) { // ✅ 正确：必须先判断有效性
actor.K2_GetActorLocation();
 }
```
        
- **真相**：TS 中的 actor 只是一个包着 C++ 指针的 JS Wrapper（包装对象）。**UE 的 GC 删除了 C++ 对象，JS 的包装对象可能还没被 V8 GC 回收**。如果不做 IsValid() 判空直接读取，会报野指针/空指针崩溃。
        
---

### 四、 容器类（TArray / TMap / TSet）与 JS 原生数组的混淆

在蓝图或 C++ 中使用的容器，传到 TS 侧时：

- **混淆点**：以为 TS 拿到 TArray 就能当作 JS 的 Array （用 map、filter、pop 等原生方法）。
    
- **Puerts 视角下的真相**：
    
    - Puerts 传给 TS 的 UE.TArray\<T> 是一个**C++ 内存映射对象**，不是 JS 的原生 []。
        
	- 你可以通过 arr.Num()、arr.Get(i)、arr.Add(elem) 来操作真实的 C++ 容器。
        
    - **性能陷阱**：如果你在 TS 里写 $ref 或用 Array.from(ueArray)，会触发一次**全量内存拷贝**。处理海量数据时要注意性能。
        
    - **修改陷阱**：在 TS 里遍历 UE.TArray 的同时删除元素，会导致 UE C++ 底层迭代器失效崩溃。
        

---

### 五、 出参（Out Parameters）与 $ref 的混淆

在蓝图中，函数节点可以有多个输出引脚（引用传递 UPARAM(ref) 或 out 参数）：

- **C++ 声明**：

    ```
    UFUNCTION(BlueprintCallable)
    void GetPlayerStats(int32& OutHP, float& OutSpeed);
    ```
    
- **蓝图表现**：节点右侧多出 OutHP 和 OutSpeed 两个返回值引脚。
    
- **Puerts / TS 表现**：
    
    - TS **不能**直接用 let [hp, speed] = GetPlayerStats()。
        
    - Puerts 引入了 $ref 和 $unref 语法来承接 C++ 的引用出参：
        
        codeTypeScript
        
```
        import { $ref, $unref } from 'puerts';
        
        let hpRef = $ref(0); // 创建引用包装
        let speedRef = $ref(0.0);
        
        obj.GetPlayerStats(hpRef, speedRef); // 传入 C++ 填充
        
        console.log("HP:", $unref(hpRef)); // 解包取出值
```

### 六、 多线程（Async/Tasks）与 V8 单线程的混淆

UE 引擎拥有强大的多线程体系（TaskGraph、Async 函数、线程池）：

- **混淆点**：以为在 C++ 的异步子线程里，可以随意调用 TS 导出的逻辑。
    
- **Puerts 视角下的致命陷阱**：
    
    - **Puerts 的 V8 虚拟机是严格单线程（主线程/GameThread）运行的！**
        
    - 如果你在 C++ 的子线程（Background Thread）中尝试调用 TS 函数、或者触发绑定了 TS 的 Delegate（委托），V8 会在底层触发 v8::Isolate::GetActive() 线程断言检查，**直接导致进程崩溃**！
        
- **正确做法**：如果 C++ 子线程计算出了结果，必须通过 AsyncTask(ENamedThreads::GameThread, [...](){ ... }) **切回游戏主线程**，才能调用 Puerts / TS 代码。

### 七，蓝图与C++热重载使用的区分**==半吊子文章(已废)==**

#### 1：内存修改（Memory）与 磁盘落盘（Disk .uasset）的死冲突（最核心）

这是导致你“每次重新打开编辑器就崩溃”的根本原因。

- **C++ 类（如 UE.BasePlayerController）**：
    
    - C++ 类是打包在 .dll / .exe 动态库里的。
        
    - 当你在 TS 里 mixin(UE.BasePlayerController) 时，Puerts 只是在**当前运行时的内存（RAM）中**修改了 C++ 的函数指针。
        
    - 每次你关闭编辑器，内存清空；重新打开编辑器，UE 从 .dll 重新加载出干净的 C++ 类。**磁盘上没有任何文件被污染。**
        
- **蓝图类（如 UE.BP_PlayerController）**：
    
    - 蓝图类是一个存储在硬盘上的 **.uasset 资产文件**。
        
    - 蓝图在内存里的结构叫 UBlueprintGeneratedClass（蓝图生成类）。
        
    - 当你 mixin 蓝图时，Puerts 会把 V8 虚拟机的 **C++ 函数指针（NativeFunc）** 强行塞进这个蓝图类里。
        
    - **致命点**：你在蓝图编辑器里改了东西并按 **Ctrl+S 保存**，UE 就会把当前内存里这个**被塞入了 Puerts 指针的畸形蓝图类，原封不动地写入硬盘上的 .uasset 文件**！
        
    - **结果**：下一次你重启编辑器，UE 去读这个 .uasset 文件，此时 TS 虚拟机还没启动，那些写入硬盘的指针全是失效的野指针/空指针。UE 资产反序列化器（FLinkerLoad）读取到无效指针，**直接触发系统级崩溃（内存越界）**！
        
==**虚幻引擎的资产序列化系统（Serialize）根本不可能把运行时的 C++ 内存函数指针写进磁盘！**==
- 蓝图 .uasset 落盘时，序列化的只有**元数据、变量默认值、类型签名和字节码数组（Script Bytecode）**。
    
- 函数指针（NativeFunc）在序列化时是**完全被跳过（Transient）**的。当蓝图重新加载时，UE 会通过符号表动态重新绑定（Bind）函数。
---

#### 2：蓝图编译（Kismet Compiler）与 重实例化（Reinstancing）机制

UE 引擎的蓝图资产有一个非常复杂的生命周期：**实时重新编译与重实例化**。

1. 当你打开 BP_PlayerController 蓝图窗口，或者修改了它的变量/节点时，UE 的蓝图编译器（Kismet Compiler）会销毁旧的类内存，并**重新生成一个全新的 UBlueprintGeneratedClass**。
    
2. 在重编译过程中，编译器会逐行校验蓝图图表里的字节码（Bytecode）。
    
3. 如果这个蓝图被 mixin 过，Kismet 编译器在校验函数图表时，会发现：“这个函数明明是个蓝图字节码函数，为什么里面挂着一个 Puerts 的 C++ Native 调度句柄？”
    
4. 这种数据结构的冲突会让 Kismet 编译器在做类型转换（Cast）或指针校验时，直接触发 **Assertion Failed 断言崩溃**。
    
 ==**破坏面向对象的隔离性（全局污染）**==
 
---

#### 3：加载时序（Loading Order）与 垃圾回收（GC）的不确定性

- **C++ 类**：引擎启动（加载 DLL）的第一时间就 **100% 永远存在于内存中**，随时随地都可以被 mixin。
    
- **蓝图资产**：采用了**按需加载（Lazy Loading）**。
    
    - 如果你在 TS 模块加载时去 mixin 一个蓝图，这个蓝图文件可能根本**还没被 UE 加载进内存**（此时 UE.BP_PlayerController 在 JS 里就是 undefined，直接报错）。
        
    - 即使加载了，如果没有任何关卡引用它，UE 的垃圾回收（GC）可能会随时把这个蓝图资产从内存中卸载掉。当它再次被加载时，之前的 mixin 钩子就彻底失效了。


- 正如你之前遇到的崩溃：在 UE 打包版本（Shipping / Development）中，==**所有原生 C++ 类（Native Class）在引擎启动阶段会被全部锁进 Disregard for GC 常驻池**==，引擎假设它的类结构和函数表是绝对不可修改的。
    
- 当你听信他的话把 mixin 注入 C++ 类时，Puerts 动态造出来的 UFunction 会瞬间打破常驻池的不可变假设。
    
- 结果就是：**游戏一启动，VerifyGCAssumptions 当场抛出致命错误，程序直接闪退！** 他鼓吹的“100% 稳定”，在打包阶段直接成了“100% 必死”。

### 九。除了Mixin以外的其他ts用法
你目前用的 **mixin（混入）模式**，本质上是一种**“==蓝图寄生写法==”**（先在编辑器里建一个蓝图壳子，然后 TS 偷偷把它的核心逻辑替换掉）。

这种写法非常适合做业务逻辑替换，但在实际工业级项目中，**官方和常规的 TS 写法远不止这一种**。
常规的 TS 写法主要有以下 **4 种典型范式**：

---
#### 常规写法一：==继承模式==（TS 直接当成 UClass 写，不用建空白蓝图）

你现在每次要写逻辑，都得去编辑器里**右键 -> 新建蓝图 -> 选父类 -> 命名为空白蓝图 -> 去 TS 拷路径 mixin**，很繁琐对吧？

**常规继承写法**允许你**完全不碰 UE 编辑器**，直接在 TS 代码里写一个类继承 UE 的基类：

```ts
import * as UE from 'ue';

// 直接继承 UE 原生 Actor，相当于在代码里动态造了一个“虚拟蓝图”
export default class TS_PlayerActor extends UE.Actor {
    // 构造函数
    Constructor() {
        let RootComp = this.CreateDefaultSubobject(
            UE.StaticMeshComponent.StaticClass(), 
            "RootComponent"
        ) as UE.StaticMeshComponent;
        this.RootComponent = RootComp;
    }

    // 重写原生生命周期
    ReceiveBeginPlay(): void {
        console.log("纯 TS 类直接跑起来了，不需要在编辑器建空白蓝图！");
    }

    ReceiveTick(DeltaSeconds: number): void {
        // 也可以直接写 Tick
    }
}
```

- **怎么用它？**  
    在任何地方直接用 TS 代码把它 Spawn 出来：

    ```ts
    import TS_PlayerActor from "./TS_PlayerActor";
    import { blueprint } from "puerts";
    
    // 把 TS 类转成 UE 识别的 UClass
    let ActorClass = blueprint.tojs(TS_PlayerActor); 
    
    // 直接在关卡中生成
    let SpawnedActor = World.SpawnActor(ActorClass, Transform) as TS_PlayerActor;
    ```
    
- **特点**：不需要污染 Content 目录，不需要维护一堆空蓝图资产，代码更纯粹。
    

---

#### 常规写法二：==纯 TypeScript 业务管理层==（POJO / 纯逻辑服务）

**初学者常犯的误区是“万物皆蓝图/皆 UObject”。**  
但实际上，游戏里的**背包管理器、网络通信层、任务系统、数据配置解析**，根本不需要挂在场景里的 Actor 上，也不需要继承任何 UE 类！

它们就是**标准的、现代的 TypeScript 纯代码**：

```ts
// 一个完全脱离 UE 引擎垃圾回收机制的纯数据管理服务
export class InventoryService {
    private static _instance: InventoryService;
    public static get Instance() {
        return this._instance || (this._instance = new InventoryService());
    }

    // 纯 TS 数据结构，访问性能极高
    private items: Map<number, number> = new Map(); 

    public AddItem(itemId: number, count: number) {
        let current = this.items.get(itemId) || 0;
        this.items.set(itemId, current + count);
        console.log(`道具增加: ${itemId}, 当前数量: ${this.items.get(itemId)}`);
    }

    public GetItemCount(itemId: number): number {
        return this.items.get(itemId) || 0;
    }
}
```

- **使用场景**：  
    Actor 捡到道具时，直接调纯 TS 单例：

    ```ts
    // 在你的 BP_PlayerController.ts 里：
    InventoryService.Instance.AddItem(1001, 1);
    ```
    
- **优势**：
    
    1. 纯 JS 对象运行在 V8 虚拟机内部，执行速度是跨语言反射调用的数倍。
        
    2. 彻底远离 UE GC 崩溃陷阱，也不用考虑 UPROPERTY()。
        

---

#### 常规写法三：==动态装配与生命周期控制==（像写 C++ 一样操控引擎）

你现在的逻辑大部分是被动触发（比如引擎启动了 Controller，再触发你的 ReceiveBeginPlay）。  
常规开发中，大量的**Actor 生成、UI 弹出、特效播放**，都是由 TS 主动调原生 API 完成的：

```ts
import * as UE from 'ue';

export class GameManager {
    
    // 动态在屏幕上弹出一个纯代码控制的 UI
    static ShowNotice(message: string) {
        let World = ...; // 获取当前 World
        let UIClass = UE.Class.Load("/Game/UI/WBP_Notice.WBP_Notice_C");
        
        // 动态创建并加到视口
        let Widget = UE.WidgetBlueprintLibrary.Create(World, UIClass, null);
        Widget.AddToViewport();
        
        // 延迟 3 秒后销毁（利用 TS 的 setTimeout，爽过蓝图里的 Delay 节点）
        setTimeout(() => {
            Widget.RemoveFromParent();
        }, 3000);
    }

    // 动态在指定位置刷一个怪物
    static SpawnMonsterAt(location: UE.Vector) {
        let MonsterClass = UE.Class.Load("/Game/Enemies/BP_Goblin.BP_Goblin_C");
        let Transform = new UE.Transform(new UE.Rotator(0,0,0), location, new UE.Vector(1,1,1));
        
        UE.GameplayStatics.BeginDeferredActorSpawnActor(...);
        // 原生 C++ 怎么写，TS 就怎么写
    }
}
```

#### 常规写法四：==原生委托与事件驱动==（替代字符串反射 FCall）

你==目前的系统==用 GameInstance.FCall.Bind((FuncName, Obj) => Obj\[FuncName]())，这种方式用的是==**字符串硬编码查函数**==，没有代码补全，==容易拼错==。

常规做法是直接监听 **UE 的原生委托（Delegate）**：

##### 1. 监听 UI 点击事件（不需要在蓝图里点“创建点击事件”）

```ts
let MyButton = this.GetWidgetFromName("Btn_Attack") as UE.Button;

// 常规 TS 监听多播委托：直接使用 .Add() 传入箭头函数
MyButton.OnClicked.Add(() => {
    console.log("攻击按钮被点击了！");
    this.DoAttack();
});
```

##### 2. 监听 GAS 的属性变动（如血量变化）

在你的 GAS 项目里，可以在 Controller 或 Character 的 TS 里直接绑定属性监听：

```ts
let ASC = this.BP_Player.AbilitySystemComponent;

// 监听 Health 属性变动委托
ASC.GetGameplayAttributeValueChangeDelegate(
    UE.AttributeSet.GetHealthAttribute()
).Add((changeData) => {
    let newHealth = changeData.NewValue;
    let oldHealth = changeData.OldValue;
    console.log(`血量发生变化: ${oldHealth} -> ${newHealth}`);
    // 直接通知 UI 刷新
});
```

#### 总结：常规 TS 项目的各模块分工

|                               |                                  |                                                  |
| ----------------------------- | -------------------------------- | ------------------------------------------------ |
| 业务场景                          | 推荐写法                             | 为什么不用 mixin？                                     |
| **美术挂资产的 Actor（主角、怪物）**       | **mixin 注入空白蓝图**（你现在的做法）         | 这种场景用 mixin 是最对的！因为模型、骨骼动画、碰撞体需要在蓝图编辑器里可视化配置。    |
| **纯逻辑管理系统（任务、背包、网络通信）**       | **纯 TypeScript 类（POJO / 单例）**    | 不需要 UE 的 Transform 和渲染，用纯 TS 写既轻量又快，完全不涉及 UE GC。 |
| **界面交互与按钮响应**                 | **TS 里获取控件后 .OnClicked.Add()**   | 避免蓝图里到处连杂乱的事件线，逻辑全部集中在 TS。                       |
| **简单动态功能（纯逻辑生成的 Trigger、弹道）** | **class extends UE.Actor（继承模式）** | 免去去 Content 文件夹手动建一大堆空白蓝图的麻烦。                    |

### 💡 开发黄金防坑口诀（总结）

1. **写接口用 C++，写逻辑用 TS，传数据用 蓝图**（避免直接用 TS 改写复杂蓝图资产）。
    
2. **Mixin 挂 C++，不挂 .uasset 蓝图**（切断资产污染路径）。
    
3. **Struct 是副本，修改要 Set 回去**（谨防以为改了结构体就能改 Actor）。
    
4. **UObject 用之前，先做 IsValid**（规避跨语言 GC 异步断层）。
    
5. **异步线程切主线程，再调 TS 代码**（保护 V8 单线程上下文）。
