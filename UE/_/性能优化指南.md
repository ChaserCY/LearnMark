# 准备工作：两个核心概念

在开始之前，我们需要记住两个经常导致游戏卡顿的“幕后黑手”：

1. **CPU（处理器）**：游戏的“指挥官”。负责算伤害、寻路、走蓝图逻辑、告诉显卡该画什么。CPU卡顿表现为游戏帧率低，且伴随经常性的“抽搐、卡死（Stutter）”。
    
2. **GPU（显卡）**：游戏的“画家”。负责画画面、算光影、渲染特效。GPU卡顿表现为画面精细度高时，帧率均匀地变低（比如只有20帧，但很平稳）。
    

下面，我们将从八个维度逐一拆解，看看如何让这“一文一武”发挥出最大实力。

# 一、 实体与架构层优化（解决海量物体的同屏难题）

在开放世界中，玩家一眼望去可能有成千上万棵树、无数的石头和建筑。如果每一个物体都作为一个独立的个体（Actor）交给CPU和GPU处理，游戏会瞬间崩溃。这一层的核心任务就是：**合并、精简、按需加载**。

### 1. 实例化渲染批量（Instanced Rendering）

每次CPU命令GPU画一次画，就叫做一次 **DrawCall（渲染调用）**。如果场景里有1000个一模一样的石头，不用实例化时，CPU需要发送1000次DrawCall，显卡和CPU都会累瘫。

- **ISM（静态实例化网格 / Instanced Static Mesh）**：
    
    - **原理解释**：把1000个重复的道具（如石块、路灯、栏杆）在内存里合并成“1个组件”。
        
    - **效果**：CPU只需要给GPU发1个DrawCall：“在这1000个位置把这个石头画出来”，DrawCall瞬间从1000降到1。
        
- **HISM（层级实例化网格 / Hierarchical Instanced Static Mesh）**：
    
    - **原理解释**：在ISM的基础上增加了“距离裁剪”和“LOD（多细节层次）”支持。
        
    - **应用场景**：最适合大面积的树木、灌木丛。离得近的树用高精度模型，离得远的自动切换成低精度，再远的直接不画。
        
- **InstancedFoliage（植被系统）**：
    
    - **原理解释**：虚幻引擎官方专门为草地、森林打造的植被工具，底层基于HISM。
        
    - **配合方案**：中近景使用Foliage，远景通过 **HLOD（层级多细节层次）** 合并成整片大网格，支撑百万级植被稳定运行。
        
- **对比 Mass 系统**：
    
    - ISM/HISM **只负责渲染**，它们只是把画面合在一起画出来，里面的草木没有任何逻辑，也不会动。
        
    - **Mass** 是虚幻引擎底层的 ECS（实体组件系统）架构，不仅能成千上万地渲染，每个实体还能独立计算AI、寻路、移动、状态。在实际项目中，二者通常是**搭配使用**。
        

### 2. HLOD（层级分层 LOD）

- **原理解释**：大世界中，当玩家离一个城镇很远时，如果还要去分别渲染每一栋房子、屋顶瓦片、窗户，纯属资源浪费。
    
- **具体做法**：HLOD 自动将一整片区域内的多个静态网格体（Mesh）和贴图**合并、烘焙**成一个超低面数的“代理模型”（Proxy Mesh）。
    
- **效果**：远距离看去，虽然是由上百个物体组成的城镇，但渲染时其实只画了1个低面数模型，大幅降低了DrawCall和CPU剔除的开销。
    

### 3. World Partition（世界分区系统）

- **原理解释**：传统的 Level Streaming（关卡流送）需要关卡设计师手动分割地图。而 World Partition（UE5核心功能）把整个游戏世界自动划分成类似于棋盘的网格（Tile）。
    
- **具体做法**：
    
    - **动态流送**：只有玩家周边的网格会被加载进内存，远处的网格自动从内存异步卸载，严控常驻 UObject（虚幻基本对象）的总量，避免内存溢出和垃圾回收（GC）卡顿。
        
    - **平滑加载**：配合**流送距离场（Streaming Distance Field）**和**预加载边界**，在玩家移动到格子边缘时提前异步加载下一个格子，消除角色移动时的 IO 卡死。
        

### 4. 自定义数据池 / 资源池（不只是 Actor 对象池）

新手一般只知道复用“人物（Actor）对象池”，但在大型项目里，这远远不够，我们必须实现更底层的资源复用：

- **材质实例池 / 粒子系统池 / 声音池**：减少频繁创建和销毁底层渲染（RHI）或音频资源带来的 GPU/CPU 瞬间卡顿。
    
- **字符串池 / 结构体数据池**：在内存中开辟一块连续区域存放高频使用的数据，避免频繁在内存堆（Heap）中分配和释放空间，防止产生内存碎片。
    

### 5. 混合架构分层（大战场落地绝招）

为了支撑极大规模的场景，业界通用的黄金法则，是将物体按**距离和复杂性**进行“三级分离”：

1. **近距离（交互层）**：使用功能完整的传统 **Actor**。比如玩家、身边的NPC、可拾取的道具。它们有完整的蓝图逻辑、物理碰撞和精细渲染。
    
2. **中距离（群体层）**：使用 **Mass ECS 实体**。比如中景处的百人小怪、飞行的子弹。它们没有繁重的Actor负担，只有高效率的底层计算。
    
3. **远距离（景观层）**：使用 **HISM/HLOD**。比如远处的建筑、背景里的森林。它们没有物理，没有逻辑，仅仅作为画面的点缀。

# 二、 CPU 主线程与逻辑优化（解决 Tick、蓝图、垃圾回收膨胀）

CPU主线程承载着游戏最核心的逻辑。如果CPU每帧要计算的东西太多，就会拖慢整个游戏的节奏。

### 1. Tick 机制全面优化

“Tick”是虚幻中每帧都会执行的生命周期函数。如果游戏里有1000个Actor在同时Tick，CPU会瞬间不堪重负。

- **事件驱动代替 Tick**：不要每帧去检测“血量是否满了”，而是只在“受到伤害”或“吃药”事件发生时去更新 UI。
    
- **降低 Tick 频率**：对于必须检测的逻辑（如距离检测），可以使用定时器（Timer）或区间检测（如每200毫秒检测一次，而不是每帧16毫秒检测一次）。
    
- **使用 Tick 分组（Tick Groups）**：将不需要在主线程同步等待的逻辑（如AI行为树、部分不影响表现的物理计算）移入异步线程计算。
    
- **远距离剔除**：当物体超出视线或距离玩家太远时，直接关闭其 Tick（SetActorTickEnabled(false)）。
    

### 2. 蓝图性能优化

蓝图虽然开发方便，但它的运行需要经过蓝图虚拟机（Virtual Machine）解析，性能开销通常是 C++ 的数倍到数十倍。

- **高频计算下沉 C++**：禁止在蓝图中写多重嵌套循环（for）、每帧进行复杂的数学运算（如矩阵变换、复杂的向量计算）。这些高频数学逻辑必须写在 C++ 中，再暴露给蓝图调用。
    
- **缓存计算结果**：不要在循环里反复获取同一个变量（如不停地获取 GetPlayerController() ），应该在初始化时用一个变量把它们存起来。
    
- **使用性能分析工具**：利用 Unreal Insights 或蓝图分析器（Blueprint Profiler）抓取耗时最长的蓝图节点，重点重构。
    

### 3. GC（垃圾回收）优化

垃圾回收（GC）是虚幻引擎清理内存中废弃对象的过程。如果内存中存在海量的 UObject，GC 在扫描内存时会导致游戏瞬间卡死。

- **源头克制**：使用对象池和不需要注册为 UObject 的 Mass 实体，从源头上减少需要 GC 扫描的对象数量。
    
- **调节 GC 运行参数**：
    
    - **延长 GC 间隔**：默认可能是几十秒一次，可以根据项目情况合理拉长。
        
    - **增量垃圾回收（Incremental GC）**：让 GC 每次只干一点活，分几十帧慢慢清理，而不是在一帧内把所有垃圾清完，从而消除卡顿感。
        
- **善用弱引用（TWeakObjectPtr）与软指针（TSoftObjectPtr）**：
    
    - 避免强引用大型资产（如大贴图、复杂的UI），防止它们常驻内存、无法被自动回收。
        

### 4. 多线程任务分离

现在的 CPU 都有很多核心，绝对不能让主线程“一核有难，多核围观”。

- **异步加载（Async Loading）**：在过场、移动过程中，用异步方式在后台悄悄加载模型、贴图和音效，不要阻碍主线程。
    
- **异步物理与寻路**：将物理碰撞查询、AI导航网格计算、声音阻挡计算全部推给异步线程。
    
- **利用 TaskGraph 与 ParallelFor**：在 C++ 中遍历超大数组（例如更新一万个子弹的位置）时，使用 ParallelFor 将任务均匀分发给所有 CPU 核心并行处理。
    

### 5. 数据结构与遍历优化

- **连续内存优先**：在 C++ 中，优先使用 TArray（连续数组）来存储实体数据，因为 CPU 缓存（Cache）非常喜欢连续的数据结构，这能大幅提升**缓存命中率**。尽量避免在高频循环中去遍历 TMap 或 TSet。
    
- **杜绝全局高频遍历**：禁止在 Tick 里使用 GetAllActorsOfClass 这种全局扫街式的函数，应当在初始化或事件触发时，手动将需要的 Actor 缓存到专门的数组里。
    
- **SoA（数组结构体）替代 AoS（结构体数组）**：
    
    - **AoS（传统面向对象）**：一个人物包含“姓名、血量、速度、坐标”，你建了一个一万名玩家的数组。当你想只更新所有人的坐标时，CPU会把姓名、血量也一起读进缓存，造成极大浪费。
        
    - **SoA（面向数据设计）**：把一万个人的“坐标”单独存放在一个连续的浮点数数组里，更新时 CPU 只读坐标，速度能提升数倍。这也是 Mass 框架高效率的秘密所在。

# 三、 渲染 GPU 全链路优化（让画面变美又不卡顿的秘诀）

在 UE5 中，Nanite 和 Lumen 是划时代的画面技术，但如果配置不当，它们也是吃显卡的“性能黑洞”。

### 1. Nanite 虚拟几何体系统

Nanite 让我们能导入千万面数的影视级模型，其核心原理是把模型切碎成微型的多边形集群（Cluster），在运行期自动做遮挡剔除和细节缩放。

- **扬长避短**：Nanite 适合海量的、不透明的硬表面物体（如山石、大楼、雕塑）。
    
- **禁用不适合的对象**：对于**透明材质、双面材质、带有动态顶点动画（如随风摇摆的草木叶子）、超小体积的物件**，尽量不要开启 Nanite。
    
- **显存控制（Nanite Stream Pool）**：设定合理的流送池大小，防止超高精度的虚拟几何体把显卡显存挤爆。
    

### 2. 光照系统混合优化

- **动静结合**：不要全部使用实时全动态 Lumen 光照。在开放世界中，大面积的背景应该使用**预渲染（烘焙）的静态光照**，仅对室内或局部需要频繁变化的场景开启动态 Lumen。
    
- **限制动态光源（Movable Light）**：动态光源非常昂贵。PC 端同屏动态光源尽量控制在 6 个以内，移动端控制在 3 个以内，其余多使用能兼顾性能与画质的固定光源（Stationary Light）。
    
- **距离场阴影（Distance Field Shadowing）**：用它来替代超远距离的实时阴影计算，能在保证远景有阴影的同时大幅降低显卡负担。
    
- **虚拟阴影贴图（VSM）**：用 VSM 代替传统的级联阴影贴图（CSM），能将大批量角色的阴影合二为一，避免影子重叠导致显卡多次绘制。
    

### 3. 贴图与材质优化

- **纹理流送（Texture Streaming）**：开启并设定全局显存预算（Pool Size）。贴图流送会根据物体离相机的物理距离，动态切换加载不同大小的 Mipmap（贴图分辨率级别）。
    
- **通道打包（Channel Packing）**：
    
    - **原理**：一张普通彩色贴图有 R、G、B、A 四个通道。我们可以把 AO（环境光遮蔽）、Roughness（粗糙度）、Metallic（金属度）这三张黑白图分别塞进同一张图的 R、G、B 通道里。
        
    - **效果**：只占用一张图的采样开销，省去了多次读取贴图的带宽。
        
- **材质 Quality Switch**：在材质蓝图中使用质量开关节点，让低配设备在运行时自动运行简化版的 Shader（着色器），关掉复杂的自发光、高阶反射等。
    
- **材质精简**：尽量避免使用大量的半透明材质（Translucent）和蒙版材质（Masked），半透明物体的相互重叠（Overdraw）是导致显卡瞬间高热卡顿的头号杀手。
    

### 4. 后处理与时序超分辨率（Upscaling）

现代高画质游戏极其依赖超分辨率技术：

- **TSR、DLSS、XeSS、FSR**：它们的原理是让显卡先渲染一个低分辨率的画面（例如 1080P），然后通过AI或时序算法将其“放大”到高清晰度（如 4K）。这能瞬间带来 30% 到 100% 的帧率飞跃。
    
- **动态分辨率（Dynamic Resolution）**：当遇到激烈战斗、特效满天飞，导致帧率严重下滑时，系统自动降低渲染分辨率以保住帧率，等画面平静后再自动恢复。
    
- **后处理剔除**：远景处自动关闭昂贵的后处理效果，如 SSAO（屏幕空间环境光遮蔽）、SSR（屏幕空间反射）、高质量景深和运动模糊。
    

### 5. 剔除体系（看不见的绝对不画）

在将画面交给显卡渲染之前，CPU 要进行严格的筛选：

- **视锥剔除（Frustum Culling）**：在镜头背后的东西，一律不画。
    
- **距离剔除（Distance Culling）**：太远的细小物件，直接不画。
    
- **遮挡剔除（Occlusion Culling）**：被大山、大楼挡在后面的箱子，一律不画。
    
- **Tile 分类剔除**：将屏幕切成 8x8 的像素块，预先判断哪些格子是没有光照、没有反射的，直接跳过这些地方的昂贵着色计算。

# 四、 物理与动画系统优化（解决碰撞计算与骨骼动画卡顿）

当游戏里有几十个角色在奔跑、打斗，布料随风飘动时，物理和动画的开销就会直线上升。

### 1. Chaos 物理优化

- **物理休眠（Sleep）**：离玩家较远、或者已经静止落地的物理刚体（如被击碎的石块、箱子），强行让它们进入休眠状态，停止每帧的物理碰撞模拟。
    
- **简化碰撞体**：绝对不能用复杂的模型表面直接做碰撞。远景、杂兵使用简单的胶囊体（Capsule）或包围盒（Box）代替，舍弃精确碰撞。
    
- **限制物理布料与布娃娃系统**：严格限制同一屏幕内能够开启物理效果的布娃娃（Ragdoll）和布料（Cloth）数量。超过一定距离，直接关闭物理模拟，转为骨骼动画模拟。
    

### 2. 动画管线优化

- **动画 LOD（Anim Budget Allocator）**：远距离的角色，不仅模型变粗糙，动画也要变粗糙。比如近处的NPC动画是 60 帧更新一次，远处的可以降到 15 帧甚至 10 帧更新一次，看起来有些卡顿但对远景来说无伤大雅。
    
- **GPU 蒙皮（GPU Skinning）**：大批量角色的骨骼变换计算极其消耗 CPU，在项目设置中开启 GPU 蒙皮，将这些计算全部卸载到显卡中并行处理。
    
- **关闭远距离高级计算**：远距离角色直接关闭 IK（反向动力学）、Control Rig（控制样脊椎）等实时身体修正计算。
    
- **动画实例池（Anim Instance Pool）**：复用已经创建好的动画组件，避免杂兵出生时因为频繁初始化动画状态机而导致游戏“咯噔”卡顿。

# 五、 AI 寻路与大规模群体优化（千人战场、RTS必备）

当同屏有上千个 AI 士兵在互相厮杀，传统的 AI 寻路算法会让主线程直接卡死。

```
                    ┌──────────────────────────┐
                    │      导航网格分块加载      │ (仅在玩家周边加载 NavMesh)
                    └─────────────┬────────────┘
                                  ▼
                    ┌──────────────────────────┐
                    │      共享感知组件体系      │ (避免每个AI都做视锥/听觉检测)
                    └─────────────┬────────────┘
                                  ▼
      ┌───────────────────────────┴───────────────────────────┐
      ▼                                                       ▼
┌──────────────┐                                        ┌──────────────┐
│  近距离 AI   │                                         │  远距离 AI   │
└──────┬───────┘                                        └──────┬───────┘
       │ (StateTree 批量行为逻辑)                                │ (关闭复杂感知检测)
       │ (基于 RVO-Avoidance 的并行避障)                         │ (直接线性移动插值)
       ▼                                                       ▼
┌──────────────┐                                        ┌──────────────┐
│ 运行 Mass AI │                                        │ 纯轻量化模拟 │
└──────────────┘                                        └──────────────┘
```

- **MassGameplay 框架**：这是虚幻引擎官方为海量单位打造的利器。它使用 **StateTree（状态树）** 批量处理 AI 逻辑，将上千个 AI 的决策逻辑压缩到几个多线程处理器中运行。
    
- **分块 NavMesh（导航网格）**：将世界导航网格按区域切片动态加载。远处的寻路网格自动卸载，避免内存中保留一整张超大地图的路径数据。
    
- **群体避障并行化（RVO-Avoidance / Mass Avoidance）**：传统的避障算法是每个 AI 互相去扫描周围的人。优化方案是采用统一的、基于多线程的全局避障计算器，避免重复扫描。
    
- **精简远距离 AI 感知**：远处的 AI 不需要每帧去睁大眼睛找敌人，可以完全关闭它们的视野、听觉检测，或者改为两秒钟才检测一次。
    
- **远距离线性移动模拟**：极远处的 AI 直接剥离寻路逻辑，只给它们两个点，让它们进行简单的线性插值移动（看起来在走即可）。
    
- **共享感知组件**：不要让每一个 AI 身上都挂一个重型的 AI Perception（感知组件），而是让它们共享一个全局的“敌人位置管理器”，直接从中读取目标数据。

# 六、 音频、UI、粒子特效优化（细节决定成败）

这些虽然是辅助系统，但积少成多，经常会成为压死骆驼的最后一根稻草。

### 1. Niagara GPU 粒子系统

- **全面转向 GPU 粒子**：除了近距离、需要与角色产生精准交互的少量粒子使用 CPU 计算外，大批量的子弹火花、爆炸碎片、烟雾特效，必须使用 GPU 粒子。GPU 粒子能在一帧内处理几十万个点的渲染。
    
- **距离剔除与最大生命周期**：当特效超出视野，或者距离太远时，直接销毁该特效或暂停它的模拟。
    
- **粒子实例化渲染**：避免每一个小火花都占用一个 DrawCall，开启粒子合批。
    

### 2. UI（UMG）优化

- **图集打包（Slate Atlas）**：把游戏里所有散落的小图标、UI 贴图打在一张超大的合图（图集）上。这样界面里就算有 20 个图标，对 GPU 来说也只是一次贴图读取。
    
- **动态 UI 控件池（Widget Pool）**：
    
    - **场景**：RPG 游戏里怪物头顶不停地飘出伤害数字、血条。
        
    - **做法**：千万不要每次飘字都去新建一个 Widget，然后销毁它。应该建立一个“飘字池”，字飘完后隐藏它并扔回池子里，下一次飘字直接改个数字拿出来用。
        
- **隐藏/不可见时暂停 Tick**：当 UI 被遮挡或处于隐藏状态时，确保其处于 Collapsed（折叠）或 Hidden 状态，并关掉它的 Tick 更新。
    

### 3. 音频系统优化

- **音效池（Audio Pool）**：音效播放器（Audio Component）也是需要复用的，避免频繁创建导致音轨爆音和卡顿。
    
- **距离衰减与最大并发限制**：设定音效的传播距离阈值。比如 50 米外发生的爆炸，直接不播放声音。同时限制同一种声音的最大播放并发数（例如同屏最多只能有 5 个杂兵同时发出惨叫）。
    
- **异步加载音频**：长背景音乐、大型环境音效采用流送（Stream）形式异步读取，不占用宝贵的内存空间。

# 七、 多人联机网络优化（万人联机、大战场的核心）

当上百、上千个玩家在同一个服务器里互动时，网络同步的开销会成指数级上升。

- **分层网络更新频率（NetUpdateFrequency）**：
    
    - 离玩家很近、正在和玩家激烈打斗的角色，每秒同步 30 次（高频）。
        
    - 远处的野怪、跑龙套的NPC，每秒同步 2 次到 5 次即可（低频）。
        
- **网络相关性（Net Relevancy）与休眠**：
    
    - 只有玩家视野范围内、或者能在地图上感知到的实体才进行网络数据复制。
        
    - 玩家看不见的远处箱子，直接让其网络复制进入“休眠（Dormancy）”状态，拒绝发送任何同步包。
        
- **数据压缩与量化（Quantization）**：
    
    - **原理**：3D 坐标在虚幻里是用高精度的双精度浮点数（Double）表示的。
        
    - **做法**：在网络传输时，把它们压缩成低精度的整数（比如把 120.3456 压缩成 120），等传到客户端后再还原。这能节省大量的带宽开销。
        
- **预测与插值（Prediction & Interpolation）**：
    
    - 客户端不需要每帧都收到服务器发来的精确坐标。服务器只发关键帧，客户端利用本地物理引擎进行“航位推算（Dead Reckoning）”，并在收到服务器数据后进行平滑插值过渡，降低同步频次。
        
- **Mass 专属网络同步**：对于同屏上千个士兵的联机游戏，放弃传统的每个 Actor 独立网络复制通道，改用 Mass 框架的**批量数据网格同步层**，将多条数据打包进一个网络包发送，突破虚幻传统的带宽瓶颈。

# 八、 打包、IO 与工程管线优化（告别加载卡顿与超大安装包）

优化不仅在游戏运行中，打包和资源管理的质量同样决定了玩家打开游戏的第一印象。

- **PSO 预缓存（Pipeline State Object）**：
    
    - **痛点**：很多游戏在第一次遇到新怪物、新技能特效时会猛烈地卡一下，这就是在临时编译 Shader（着色器）。
        
    - **解决方案**：在游戏打包时，提前把所有可能用到的 Shader 编译好并打包进安装包，在游戏启动或过场加载时预热缓存（PSO Cache），彻底消除游戏内的首次渲染卡断。
        
- **资源分块打包（Pak Chunking）**：
    
    - 将大世界的资产切分成多个独立的 .pak 文件。玩家下载或加载时，按需异步读取对应区域的资源包，避免启动时一次性读入过多无用数据。
        
- **禁用不使用的引擎模块**：
    
    - 如果项目是偏写实的、不需要卡通渲染，或者不需要 Substrate（次世代材质框架）、虚拟纹理（Virtual Texture）、硬件光线追踪等，直接在项目设置（Project Settings）和插件（Plugins）中将其关闭。这能大幅简化 Shader 变体数量，减少打包体积，并缩短打包时间。
        
- **内存预算桶（Memory Buckets）**：
    
    - 针对不同配置的硬件（如低端手机、高配PC），预设不同的显存和内存上限预算（Bucket Limits），并在运行期动态调整纹理加载上限。

# 核心区分：三大方案各自解决什么问题？

新手在面对层出不穷的优化词汇时很容易混淆。这里做一个直观的横向对比：

|   |   |   |   |   |
|---|---|---|---|---|
|方案类别|代表技术|它能解决什么？|它**无法**解决什么？|适用场景|
|**对象池**<br>(Object Pool)|ActorPool|解决高频创建/销毁带来的**瞬间卡死**（如频繁生成子弹）。|无法降低同屏渲染开销，无法提升 CPU 遍历数组的性能。|几十至几百个频繁生死的短命对象（如弹壳、漂字）。|
|**Mass 框架**<br>(ECS 架构)|MassGameplay|解决海量单位带来的 **CPU 逻辑计算瓶颈、GC 扫描负担**。|本身不提供高阶渲染黑科技（仍需配合 HISM 渲染）。|千人同屏大战场、密集丧尸群、大都市人群和车流。|
|**引擎原生技术**|Nanite / HLOD / WP|解决大世界背景带来的 **GPU 渲染极限、IO 加载卡顿**。|无法解决复杂的动态 AI 逻辑或联机同步问题。|超大开放世界、复杂地形、高精度建筑群渲染。|
