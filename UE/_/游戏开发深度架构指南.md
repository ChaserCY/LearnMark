# 现代游戏全栈开发：从底层实体到跨层工程的深度架构指南

在游戏开发中，架构的目标是平衡“运行性能”与“逻辑灵活性”。我们将一套完整的游戏系统分为四层：底层世界实体、中层业务模块、上层UI界面以及跨层通用工程。

---

## 一、 底层：游戏实体架构（World Entity Architecture）

**作用：** 决定物体在内存中如何排列，数据如何被读取，逻辑如何驱动。

### 1. ECS 流派（数据驱动，极致性能）

#### [1] 标准 ECS (Entity-Component-System)

- **实现：** Entity 是一个递增的 int ID；Component 是纯 struct；System 是 for 循环逻辑。代表：Unity DOTS, flecs, entt。
    
- **大白话解释：** 就像图书馆的卡片索引。Entity 只是一个图书编号（如：1024）。Component 是一张张卡片，一张写着“重量 1kg”（数据），一张写着“尺寸 20cm”。System 则是自动扫描仪，只负责把所有贴有“重量卡片”的图书拿去称重，它不需要知道书名是什么。
    
- **具体落地实现：**
    
    codeC#
    
    ```
    // Component：只有数据，绝无逻辑
    public struct PositionComponent { public float x; public float y; }
    public struct VelocityComponent { public float vx; public float vy; }
    
    // System：只有逻辑，每帧遍历匹配了特定组件的 Entity
    public class MovementSystem {
        public void Update(List<Entity> entities) {
            // 通过位掩码（Bitmask）快速过滤出同时拥有 Position 和 Velocity 的实体
            foreach (var entity in Query(typeof(PositionComponent), typeof(VelocityComponent))) {
                ref var pos = ref entity.Get<PositionComponent>();
                ref var vel = ref entity.Get<VelocityComponent>();
                pos.x += vel.vx * Time.deltaTime;
                pos.y += vel.vy * Time.deltaTime;
            }
        }
    }
    ```
    
- **真实运行场景：** 战场上有 5000 支射出的箭。每支箭（Entity）只有坐标和速度数据。没有渲染和碰撞时，它们在内存里只是紧凑的数字。MovementSystem 在后台的多线程中飞速遍历这些数字并更新位置，不需要运行任何庞大的物体类。
    

---

#### [2] SOA-ECS (Structure of Arrays)

- **原理：** 传统的对象数组是 AOS（A-X-Y-Z, B-X-Y-Z），而 SOA 将相同属性排在一起（XXXX, YYYY）。效果：极致的 CPU 缓存命中率。当 System 只需要处理坐标时，CPU 预取到的全是坐标，没有杂质数据。
    
- **大白话解释：** 传统的“对象数组（AOS）”就像你去超市买水果，每个袋子里装 1 个苹果、1 个香蕉、1 个橘子。你想吃光所有苹果，就必须把每个袋子都打开，拿出苹果，丢掉袋子。而“结构体数组（SOA）”是超市里直接摆了一整箱苹果、一整箱香蕉、一整箱橘子。你直接把苹果箱子拖走吃个痛快，中间没有任何多余的动作。
    
- **具体落地实现：**
    ```c#
    // 传统 AOS（性能差，内存不连续）
    struct Particle { float x; float y; float scale; int color; }
    Particle[] particles = new Particle[10000]; // 内存里 x, y, scale, color 交替排列
    
    // 现代 SOA（性能高，内存连续）
    struct ParticleContainer {
        public float[] x;     // 所有粒子的 x 坐标全挨在一起
        public float[] y;     // 所有粒子的 y 坐标全挨在一起
        public float[] scale;
        public int[] color;
    }
    ```
    
- **真实运行场景：** 在万人同屏的割草游戏（如《真三国无双》或《吸血鬼幸存者》）中，20,000 个小怪只需要更新位置。CPU 每次从内存往高速缓存（L1/L2 Cache）加载数据时，顺便把后面紧挨着的几百个小怪的坐标也一起“预加载”进去了。CPU 计算指针无需跳转，运算速度达到极限。
    

---

#### [3] Hybrid 混合 ECS

- **实现：** 让传统游戏对象（GameObject/Actor）持有 ECS 的 Entity ID。场景：渲染表现用传统对象以便于美术编辑，底层逻辑（如海量弹幕计算）用 ECS 跑数据。
    
- **大白话解释：** 美术和策划习惯了在编辑器里拉模型、调灯光、配材质。如果你让他们对着冷冰冰的代码写 struct，工作流就断了。Hybrid 模式就是“逻辑归电脑管（ECS 实体负责计算位置），长相归人类管（GameObject 负责播放动画和特效）”。
    
- **具体落地实现：**
    ```c#
    public class GameObjectSyncComponent : MonoBehaviour {
        public uint LinkedEntityID; // 挂载在 Unity 传统物体上，绑定底层 ECS 实体 ID
    }
    
    // 同步 System
    public class SyncTransformSystem {
        public void Update() {
            foreach (var entity in entities) {
                var pos = entity.Get<PositionComponent>();
                // 将底层纯数据计算出的坐标，每帧同步给上层的物理 GameObject 渲染体
                GameObject go = GetGameObjectByEntityID(entity.ID);
                go.transform.position = new Vector3(pos.x, pos.y, 0);
            }
        }
    }
    ```
    
- **真实运行场景：** 3D 太空射击游戏。太空中密密麻麻的 5000 颗陨石在底层以纯数值（ECS）运行轨迹计算和碰撞预测。当陨石靠近玩家视野时，系统才动态为它绑定一个精细的 3D 石头模型（GameObject），进入玩家视线；远离时，销毁模型，保持底层纯数据计算。

### 2. OOP 组件化 EC 架构（无System，传统引擎原生）

- **原理：** 实体（Entity）是一个胖对象，通过 AddComponent 挂载脚本。脚本里既有数据（HP）又有逻辑（Update）。没有单独 System，UE/Unity 原生。
    

#### [1] UE：Actor + UActorComponent

- Actor=实体，Component挂载属性、逻辑，GAS就是基于这套组件拓展。
    
- **大白话解释：** Actor 就像一个基础的机器人空壳。如果你想让它能跑，就给它插上一个“移动芯片（MovementComponent）”；想让它放火，就挂载一个“魔法芯片”。每个芯片自己管自己的运算，彼此独立。
    

#### [2] Unity：GameObject + MonoBehaviour

- 最常用原生架构，组件挂载脚本，缺点海量对象 GC 高、内存碎片化。
    
- **具体落地实现：**
    ```c#
    public class PlayerController : MonoBehaviour {
        private float hp = 100; // 数据和逻辑死死绑在一起
        void Update() {
            if (hp < 0) PlayDeathAnimation();
        }
    }
    ```
    
- **底层弊端：**
    
    1. **内存碎片：** MonoBehaviour 属于 C# 堆内存上的引用类型。当你在游戏中频繁 Instantiate（实例化）和 Destroy（销毁）小怪、子弹时，内存地址会变得像筛子一样千疮百孔，导致频繁触发垃圾回收（GC），造成游戏卡顿。
        
    2. **调用开销：** 引擎从底层 C++ 跨界调用 C# 的 Update 虚函数是有很大性能开销的。如果场景里有 2000 个挂载了 Update 的小怪，即使脚本里什么都不写，每帧光是空调用都会吃掉几毫秒的 CPU 时间。
        

#### [3] Cocos：Node + Component

- 同组件化 OOP 思路，核心架构与 Unity 极其相似，适用于轻量级或 Web、小游戏端。

---

### 3. 老旧继承式架构（淘汰，早期端游）

- **做法：** BaseObject → Character → Player → Hero。层级继承臃肿，现在新项目基本不用。
    
- **死因：** “菱形继承”灾难。如果想让“玩家”和“火把”都能发光，你得在基类写发光逻辑，导致基类极其臃肿（胖基类）。
    
- **大白话解释：** 假设你定义了一个“哺乳动物类”，生出“人”和“蝙蝠”。人能说话，蝙蝠能飞。现在策划突然要求设计一个能飞、能说话的“鸟人”，你该继承谁？如果多继承，代码会变得极其混乱。如果把“飞”和“说话”都写在最顶层的基类里，那“猪”也能飞、能说话了，最终基类代码超过几万行，谁也不敢改。

## 二、 中层：业务专用框架（基于底层实体架构，实现战斗/AI/任务/数值）

**作用：** 在 Actor/ECS 之上，封装某一类业务的专用框架，GAS 属于其中战斗分支。

### 1. 战斗系统框架

#### [1] GAS（UE专属/思想通用）

- ASC组件+Ability+GameplayEffect+Attribute，RPG/动作首选，BUFF、技能、属性计算。
    
- **大白话解释：** 就像一个高度标准化的规则卡牌游戏。
    
    - **ASC（组件）：** 是每个玩家身上的“裁判”。
        
    - **Ability（技能）：** 是一张张“卡牌”（如：火球术）。
        
    - **GameplayEffect（效果）：** 是一张张“Buff纸条”（如：冰冻 3 秒，每秒扣 10 血）。
        
    - **Attribute（属性）：** 是卡牌上的数值（如：当前生命值、魔法值）。
        
- **具体落地实现：**
    
    1. 玩家按下 [Q] 键。
        
    2. **ASC** 检查玩家身上是否有 State.Debuff.Silence（沉默）标签。
        
    3. 若没有，激活 **Ability_Fireball**。该 Ability 扣除 AttributeSet.MP（魔法值）。
        
    4. 子弹击中敌人，向敌人 ASC 投递一个 **GameplayEffect_Burn**。
        
    5. 该 Effect 包含一个 GameplayTag 叫 State.Debuff.Burning。在此状态下，敌人无法进入隐身状态（隐身 Ability 的触发前置条件是“不带 Burning 标签”）。
        
---

#### [2] FSM有限状态机

- 角色普攻/受击/跳跃状态切换，小型小游戏、2D游戏。
    
- **大白话解释：** 角色任何时候只能处于一种状态。比如你不能一边在空中间“跳跃”，一边在地上“跑步”。它规定了状态之间跳转的路线图。
    
- **具体落地实现：**
    ```c#
    public interface IState {
        void Enter();
        void Update();
        void Exit();
    }
    
    public class StateMachine {
        private IState currentState;
        public void ChangeState(IState newState) {
            currentState?.Exit();
            currentState = newState;
            currentState.Enter();
        }
    }
    ```
    
- **真实运行场景：** 2D 横版格斗游戏。玩家在 Idle（待机）状态。按下攻击键，状态机立刻执行 Exit() 退出待机，调用 ChangeState(AttackState)。在 AttackState 中，玩家无法通过按下方向键触发跑步，必须等攻击动画播完（或者硬直结束），状态机切换回 Idle 状态后，跑步指令才有效。这极大地保护了动作逻辑的干净利落。
    
---

#### [3] 数值公式框架

- 属性计算公式解耦，配置表驱动，伤害、攻防计算统一托管。
    
- **大白话解释：** 传统的伤害代码写死在角色身上：damage = attack - defense。如果有一天策划想要加入“破甲”、“暴击率”、“等级压制”等复杂的算式，你就必须重写代码。数值公式框架就是把公式做成独立的计算黑盒。
    
- **具体落地实现：**
    
    - 利用表达式解析引擎（如解析字符串 (Attacker.ATK * 1.5) - Target.DEF），或者使用专门的数值修饰器模式（Modifier）。
        
    - 所有的乘算、加算、减算，都按照固定的优先级（Base -> Add -> Multiply -> Final）在一个中央计算器里跑完，输出最终伤害数值给扣血逻辑。
        
---

### 2. AI 行为框架

#### [1] BT行为树(BehaviorTree)

- UE原生行为树、Unity行为树，NPC巡逻、追击、逃跑。
    
- **大白话解释：** 这是一个决策树，从上到下、从左到右执行。
    
    - **Sequence 节点（顺序执行）：** 必须每一步都成功。比如“发现敌人 -> 奔跑过去 -> 发动攻击”。如果中间“奔跑过去”被墙挡住了（失败），攻击就不会触发。
        
    - **Selector 节点（选择执行）：** 只要有一步成功就结束。比如“血量过低？跑去吃药包” 失败了就执行 “和敌人死拼”。
        
- **具体落地实现：**  
    行为树每帧通过一个称为 Tick 的脉冲来运行。从 Root 节点开始，将控制权交给子节点，子节点返回 Success（成功）、Failure（失败）或 Running（正在执行，下一帧继续）。
    
- **真实运行场景：** 巡逻的守卫。行为树第 1 分支检查：有敌人吗？返回失败。树继续走到第 2 分支：执行巡逻路径。NPC 走向 A 点，节点返回 Running。当玩家突然出现在视野里，第 1 分支检查返回 Success，行为树立刻打断巡逻分支，转而执行追击逻辑。
    
---

#### [2] GOAP（目标导向规划）

- 开放世界高智能NPC，自主规划行为（找食物、躲危险）。
    
- **大白话解释：** 行为树是提前规定好的“死板流程图”，而 GOAP 则是给 AI 目标和工具，让它自己算路。比如目标是“肚子不饿”，工具（Action）有“砍树”、“点火”、“烤肉”、“吃肉”。AI 会像导航软件一样，自动算出一套“砍树 -> 收集木头 -> 生火 -> 烤肉 -> 吃肉”的动作链条。
    
- **具体落地实现：**
    
    - 每个 Action 都有 **Preconditions（前置条件）** 和 **Effects（产生效果）**。
        
    - AI 确定终极状态（Goal，如 Hungry = false）。
        
    - 使用类似 A 寻路算法* 在“动作空间”里逆向检索。找到一条成本最低（Cost）的 Action 链，并顺序执行。
        
---

#### [3] HTN分层任务网络

- 比GOAP层级更高，复杂宏观AI逻辑。
    
- **大白话解释：** 类似军队里的指挥体系。将军下一个宏观命令（Compound Task）：“占领前方山头”。团长把命令分解（Decompose）为：“一连正面佯攻，二连包抄后路”。排长把一连的任务分解为原子动作（Primitive Task）：“跑、趴下、射击”。
    
- **具体落地实现：**
    
    - 将逻辑划分为“宏观复合任务”和“原子底层动作”。
        
    - 规划器（Planner）从宏观任务开始，通过一系列预设的“方法（Methods）”递归地尝试将其分解，直到分解为纯粹的底层 Action 序列。由于分解路线是预设的，它比 GOAP 的全局盲目搜索快得多，能承载数量庞大的高动态战术决策。

### 3. 模块框架：背包、任务、剧情

#### [1] 配置表驱动架构

- 所有道具、任务、文案Excel导出JSON/Protobuf，代码不硬编码数值。
    
- **大白话解释：** 游戏里的每一个道具属性、NPC对话绝对不能直接写在代码里。必须要用 Excel 表格写好，一键转成数据包（JSON、CSV 或 Protobuf 二进制文件）。代码只写读取和解析这些数据的通用规则。
    
- **具体落地实现：**
    ```c#
    // 道具数据模板
    public class ItemConfig {
        public int ItemID;
        public string Name;
        public string Description;
    }
    // 读取逻辑
    public class ConfigManager {
        public Dictionary<int, ItemConfig> ItemTable;
        public void Load() {
            string json = File.ReadAllText("ItemConfig.json");
            ItemTable = JsonConvert.DeserializeObject<Dictionary<int, ItemConfig>>(json);
        }
    }
    ```
    

#### [2] 事件总线架构

- 模块解耦，背包使用道具→发布事件→任务系统、成就系统自动监听。
    
- **具体落地实现：**  
    通过全局监听机制消除模块间的互相依赖（解耦）。

    ```c#
    // 定义一个全局事件中心
    public static class EventBus {
        private static Dictionary<string, Action<object>> listeners = new();
        public static void Subscribe(string eventName, Action<object> action) {
            if (!listeners.ContainsKey(eventName)) listeners[eventName] = null;
            listeners[eventName] += action;
        }
        public static void Publish(string eventName, object data) {
            if (listeners.ContainsKey(eventName)) listeners[eventName]?.Invoke(data);
        }
    }
    ```
    
- **真实运行场景：** 玩家喝下一瓶药水。**背包系统**扣除道具并广播 EventBus.Publish("OnUseItem", itemID)。此时，**成就系统**（听着呢）收到消息发现玩家喝了药水，给“百药之王”成就进度+1；**任务系统**（也听着呢）发现符合“使用一瓶血药”的任务要求，把任务标记为完成。背包系统自始至终不需要知道成就系统和任务系统的存在，代码干净到了极致。

## 三、 上层：UI架构（只做界面，MVC家族全系列）

**作用：** 全部用于HUD、弹窗、背包、设置页，不参与场景实体逻辑。

### MVC原生及五大变种

#### [1] MVC

- M(数据) V(显示) C(控制器中转)，早期Unity/原生小程序UI。
    
- **原理：**
    
    - **Model：** 只存数据，比如 Gold = 10。
        
    - **View：** 纯界面元件，比如金币文字 UI。
        
    - **Controller：** 桥梁。玩家点击“购买”按钮（View 事件），Controller 收到通知，计算扣减 Model 里的 Gold，再通知 View 刷新文字。
        
- **致命缺点：** Controller 经常会写得极其庞大，且 View 和 Model 之间有时会产生直接交叉调用，解耦不够彻底。
    

---

#### [2] MVVM（目前游戏UI主流）

- V(界面) ←双向绑定→VM(视图模型)，不用手动刷新界面，数据变UI自动变，UGUI+DoTween大量使用。
    
- **大白话解释：** 魔法镜子。你（数据）变胖了，镜子里的影像（UI）自动就变宽了。你不用拿画笔去手动修改镜子里的画面。
    
- **具体落地实现：**  
    通过属性监听器（Observable）或属性改变通知事件（UniRx 响应式编程框架很擅长做这个）。
	
    ```c#
    // ViewModel 层
    public class GoldViewModel {
        public ReactiveProperty<int> Gold = new ReactiveProperty<int>(0);
    }
    // View 层绑定
    public class GoldView : MonoBehaviour {
        public Text goldText;
        public GoldViewModel viewModel;
        void Start() {
            // 绑定：一旦 Gold 的值变了，自动调用 Text.text 赋值，彻底告别手动更新
            viewModel.Gold.Subscribe(newGold => goldText.text = newGold.ToString());
        }
    }
    ```
    
---

#### [3] MVP

- V只负责显示，P中间人，View不持有Model，强解耦，大型项目客户端UI。
    
- **大白话解释：** 类似严格的传话制度。View 是聋子，Model 是盲人。Presenter 在中间。View 点了按钮，Presenter 收到后去改 Model。Model 变了，Presenter 再去告诉 View 改文字。两者死活见不到面，也无法产生对方类型的直接引用。
    
- **核心好处：** 极高测试性。由于逻辑全部锁在 Presenter 里，不需要启动游戏引擎渲染 UI，直接用代码就能对 Presenter 进行自动化测试（Unit Test）。
    

---

#### [4] MVU（Model-View-Update）

- Model-View-Update，函数式UI，Godot、Flutter。
    
- **大白话解释：** 幻灯片。你的界面状态是一个只读的“截屏”（Model）。当有任何操作（如点赞）时，触发一个 Update 函数，这个函数会生成一个崭新的“截屏”（新 Model），View 丢弃旧画面，完全根据新“截屏”重新渲染。
    
- **实现逻辑：** 单向数据流。State + Action -> New State -> View。界面极度纯粹和安全，绝不会出现局部状态不同步的诡异 Bug。
    
---

#### [5] CleanUI分层架构

- 清洁架构思想拆分UI，接口隔离，超大型项目（原神、黑神话客户端）。
    
- **大白话解释：** 将 UI 按照业务领域做物理切分。游戏战斗 UI、大地图 UI、社交 UI，它们在工程里属于完全不同的物理文件夹、甚至编译成不同的动态链接库（DLL / Assembly）。
    
- **实现逻辑：** 使用依赖注入（DI，如 Zenject/VContainer），各模块间禁止交叉引用，所有通讯必须走严格定义的公共 Interface 隔离，保证一个 UI 开发团队修改背包逻辑时，绝对不会把隔壁组写的聊天 UI 弄崩溃。
    

---

### 补充：UI资源架构（UIPool 对象池）

- **实现：** 弹窗复用，频繁打开关闭减少GC，属于UI配套工程架构。
    
- **大白话解释：** 每次打开背包界面，如果都去加载资源并创建一个新的 UI 实例，关闭时又销毁它，手机就会卡顿（GC）。UIPool 的做法是：关闭背包时，不销毁，只把它移到屏幕外面或隐藏（SetActive(false)），并塞入一个备用队列（栈）。下次再开背包时，直接从队列里拿出来激活显示。
    
---

## 四、 跨层通用架构（独立三层之外，贯穿客户端全工程+服务端）

### 1. 网络层架构

#### [1] RPC架构

- UE NetRPC、Unity PhotonRPC，客户端服务端函数远程调用。
    
- **大白话解释：** 远程打电话下命令。你在客户端想开火，调用本机的 Server_Fire() 函数。框架底层自动把这个调用打包，通过网络发给服务器，服务器在它的进程里帮玩家执行 Fire() 逻辑。
    
- **具体落地实现：**  
    通过网络库对方法打上标记（Attribute），并在底层实现字节序列化。

    ```c#
    [ServerRPC] // 这是一个服务器运行的方法
    public void CmdUseItem(int itemID) {
        // 底层库自动拦截调用，打包 [PlayerID, MethodID, itemID] 通过 TCP/UDP 发送给服务端执行
    }
    ```
    
---

#### [2] 同步机制（帧同步 & 状态同步）

- **帧同步（Lockstep）：**
    
    - **原理：** 客户端只上传玩家的指令（按下了W键、开了一枪）。服务端每秒把所有人的操作指令打包群发（如一秒 30 帧）。客户端根据这些指令，在本地运行完全一致的物理和逻辑模拟。
        
    - **要求：** 极其苛刻。所有客户端的运算必须绝对一致（确定性），浮点数计算、随机数种子在各端不能差一分一厘，否则就会导致“不同步（Desync）”。常用于 MOBA、格斗。
        
- **状态同步（State Sync）：**
    
    - **原理：** 服务器是唯一真理。服务器计算怪物的血量、所有人的位置，然后将这些“结果”不断广播给客户端。客户端收到后只负责把这些结果“翻译”并渲染出来。
        
    - **特点：** 防作弊能力极强，客户端即使修改本地内存也没用，因为服务器只认自己的计算结果。常用于 MMORPG、棋牌。
        
---

#### [3] 网关分层架构

- 客户端→网关→逻辑服→数据库（服务端标准分层）。
    
- **大白话解释：** 客户端玩家不能直接连最核心、最脆弱的“游戏战斗服务器（逻辑服）”。因为直接连容易受到黑客 DDoA 攻击。玩家必须先连网关（Gate）。网关像前台，负责检查你有没有买票（鉴权）、把你说的暗号翻译成逻辑服懂的语言（解密分发），再把消息传进后院的逻辑服。
    
---

### 2. 资源&热更架构

#### [1] 分包+AB资源包架构(Unity)/Pak(UE)

- 资源分包加载、按需加载。
    
- **大白话解释：** 手机游戏包体不能动辄几百G。AB包和Pak包技术是将模型、贴图、音乐打包成一个个压缩包放到服务器上。玩家玩到第一关，游戏在后台静默下载第一关需要的包；玩到第二关再下第二关的包，实现包体极小化。
    

#### [2] Lua/JS/TS/C# 热更架构

- XLua、ToLua、UnLua、Puerts、HybridCLR，逻辑脚本热更不用整包更新。
    
- **大白话解释：** 移动端（iOS/Android）应用商店审核一次非常漫长。如果逻辑出了 Bug，不能让玩家重新下载 2G 的安装包。热更技术在游戏包里内置了一个脚本解释器（虚拟机）。每次进游戏，它会去云端下载几个 KB 的代码脚本（Lua 或 TypeScript），动态替换掉本地有 Bug 的旧逻辑。
    
---

### 3. 服务端整体架构（后端）

#### [1] 单体架构

- 小游戏、羊了个羊简易后端。
    
- **实现：** 所有的登录、匹配、战斗、数据库读写全部写在一个进程里。开发极其简单，但如果登录的人太多，整台服务器就会直接卡死宕机。
    

#### [2] 微服务架构

- 网关服、战斗服、排行服、用户服拆分，大型网游。
    
- **大白话解释：** 分工明确的流水线。登录有专门的“登录服务”，匹配有“匹配服务”，战斗有“战斗服务”。如果由于某些原因聊天功能崩了，玩家最多无法在世界频道说话，但绝对不会影响他们正常战斗和充值，系统容灾能力极强。
    

#### [3] DDD领域驱动架构

- 大型MMO后端领域拆分（用户域、道具域、战斗域）。
    
- **实现：** 核心是高阶的业务限界上下文。通过梳理现实业务，将大后端解耦为数个独立的“领域模型”。领域内部高度聚合，领域之间通过严格的消息格式调用。这极大地规范了高复杂度业务（如几十万行代码的 MMO）在开发中的结构，不至于让业务逻辑乱成麻线。
    
---

### 4. 通用插件架构

- 插件化模块化，核心框架与业务隔离，插拔式功能（SDK插件：微信登录、广告）。
    
- **大白话解释：** 就像电脑的 USB 接口。电脑本身（核心框架）不需要关心你插进来的是键盘、鼠标还是暖手宝。通过标准接口协议，第三方 SDK（如广告、SDK登录）可以随时插拔，不需要去修改任何游戏最底层的关键代码。
    
---

## 五、 落地组合示例（举例UE项目，面试通关模版）

1. **底层实体：** 场景里的杂兵小怪、飞行的海量弹幕子弹采用底层 **EnTT ECS** 进行数据排布，保障同屏 5000+ 单位不卡顿；而玩家控制的复杂主角采用原生的 **Actor+UActorComponent**，方便美术连动画蓝图。
    
2. **中层业务：** 主角的战斗逻辑、血量修改、技能连招与状态互斥使用 **GAS**；NPC 的 AI 行为使用原生的 **BT行为树**；所有技能数值、掉落概率全由 **Excel 配置表驱动**。
    
3. **上层UI：** 游戏内的背包系统、商城界面、HUD 属性反馈全部采用 **MVVM** 进行数据与 View 的双向绑定，彻底告别手动更新。
    
4. **跨层工程：** 脚本逻辑使用 **Puerts** 运行时（利用 TypeScript 开发并支持热更新），资源通过 **Pak** 分包加载，网络通讯使用 **UE 原生 RPC 状态同步**，后端采用**分布式微服务**。

## 六、 一句话总结区分

- **底层 EC/ECS：** 解决内存“怎么排”、物理物体“怎么存” —— **决定性能上限。**
    
- **中层 GAS/BT/FSM：** 解决玩法规则“怎么写”、AI“怎么动” —— **决定好不好玩。**
    
- **上层 MVC/MVVM：** 解决界面“怎么画”、数据“怎么看” —— **决定开发效率。**
    
- **跨层架构：** 解决工程“怎么联、怎么更、怎么打包后端” —— **决定商业运营。**
