# 1.游戏实例（GameInstance）：
|类 (Class)|生命周期 (存活时间)|适用场景|比喻|
|**GameMode**|**仅当前关卡**。<br>换地图就销毁。|关卡的规则（如：限时5分钟，胜利条件）。|房间里的裁判。|
|**PlayerController**|**仅当前关卡**。<br>换地图通常会重建。|玩家的输入控制、HUD显示。|你的手柄/键盘。|
|**SaveGame**|**永久（硬盘）**。<br>关机也不丢。|写文件到硬盘，用于存档。|你的日记本/硬盘。|
|**GameInstance**|**整个游戏运行期间**。<br>换地图不丢，关游戏才丢。|**跨关卡传数据**（内存中）。|**你的背包/大脑记忆。**|

**注意区分 SaveGame 和 GameInstance：**
- **GameInstance** 是存在**内存（RAM）** 里的。游戏关掉，数据就没了。
- **SaveGame** 是存在**硬盘**里的。
- **通常做法**：游戏运行时，把数据存在 GameInstance 里方便随时读写；当玩家到达存档点或退出游戏时，把 GameInstance 里的数据保存到 SaveGame（硬盘）里。

缓存保存：保存到电脑磁盘，重开游戏数据依然存在

# 2.宏和函数
![](图片/UE/学习/学习概念/IMG-20260718014107626.png)


- **函数 (Function)** 就像是“查字典”**。==引用==
    - 全班同学共用这一本字典。当你需要查一个字时，你跑去翻那本字典，查完了再回到座位上继续写作业。
        
- **宏 (Macro)** 就像是**“复印机/复制粘贴一整坨/复合节点”**。==复制==
    - 当你使用宏时，引擎会在编译时把宏里面的所有节点群，**原封不动地复制粘贴**到你放置宏的位置。
使用：函数用于输入输出计算(计算和结果)，宏用于封装整个逻辑群体(执行)
区别：
 1. 能否使用“潜流节点” (Latent Nodes) —— 最核心的区别
 2. 执行流（Execution Pins）的自由度
 ——宏：非常自由       函数：只能一个输入一个输出（一天执行流）
 3. 底层原理与性能 (Call vs Copy)
 ——函数：省内存，修改方便，速度快      宏：复制的开销大，体积膨胀
4.  作用域与通配符 (Scope & Wildcards)
——函数：静态，都可以调用           宏：指定父类，只能是这个父类子类才可以用，支持通配符IsValid检查

# 3.蓝图枚举

## 整数转枚举，Select(选择)节点
### 1. 枚举（Enum）有什么作用？

枚举的核心作用是**为了让逻辑更清晰、更易读，并防止出错**。

- **命名状态（可读性）：**
    
    - **不用枚举：** 假设你要做一个门的开关逻辑。你可v

- 能会用整数（Integer）变量：0 代表关，1 代表开，2 代表锁住。过两个月你再看代码，你可能会忘 2 到底是什么意思。
        
    - **用枚举：** 你创建一个枚举叫 E_DoorState，里面有 Open、Closed、Locked。在蓝图中，你看到的不再是数字，而是直接写着 Locked 的选项。
        
- **控制流程（Switch on Enum）：**
    
    - 这是枚举最强大的地方。你可以使用 **"Switch on [枚举名]"** 节点。这个节点会自动分叉出所有定义好的状态（如开、关、锁）。这比写一堆 Branch (If) 节点要整洁得多。
        
- **限制选项（安全性）：**
    
    - 当你在蓝图中公开一个变量给别人（或自己在编辑器细节面板）调节时，如果是整数变量，你可以输入 9999，这可能会导致程序崩溃。但如果是枚举变量，你只能从下拉菜单里选你定义好的那几个选项，绝对不会选错。
        

---

### 2. 枚举与普通变量（如 Int, Float, Boolean）有什么区别？

本质上，枚举在计算机底层**就是整数（Byte/Integer）**（第1个选项是0，第2个是1，以此类推），但在使用体验上有巨大区别：

|   |   |   |
|---|---|---|
|特性|普通变量 (Integer/Boolean)|枚举 (Enum)|
|**值的范围**|开放的。例如整数可以是 -20亿 到 +20亿。|**封闭的**。只能是你预先定义好的那几个选项。|
|**表现形式**|数字或勾选框。|**下拉列表（Dropdown List）**。|
|**语义**|只有数值，没有名字（除非你注释）。|**有明确的名字**（如 Idle, Run, Jump）。|
|**逻辑分支**|需要比较（Does A == 1?）。|直接分流（Switch on...）。|

---

### 3. 它是不是算一个“全部蓝图可直接用的设置对应蓝图对象的变量”？

这里需要纠正一个概念，你的理解**对了一半**。

**它的定义是全局的，但它的值是局部的。**

让我们拆解一下这个概念：

#### A. “全局定义” (Global Definition) —— 是的

当你创建一个枚举资产（在内容浏览器右键 -> Blueprints -> Enumeration）时，这个**枚举类型（Type）** 就变成了整个项目通用的。

- 你可以在**角色蓝图**里用这个枚举。
    
- 你可以在**UI蓝图**里用这个枚举。
    
- 你可以在**关卡蓝图**里用这个枚举。
    
- **大家都能“看见”并使用这个下拉菜单的结构。**
    

#### B. “全局变量” (Global Variable) —— 不是

这**并不**意味着你在一个蓝图里把枚举选成“A”，全世界所有蓝图里的这个枚举都会变成“A”。

- **举例：**
    
    - 你定义了一个枚举 E_Team（红队、蓝队）。
        
    - 你创建了 **10个** 小兵蓝图，每个小兵都有一个 E_Team 类型的变量。
        
    - 你可以把小兵A设为“红队”，把小兵B设为“蓝队”。
        
    - **它们互不干扰。**
        

**总结你的疑问：**  
枚举本身是一个**“模板”或“类型”**（就像 Integer 是一种类型），一旦创建，所有蓝图都可以创建这种类型的变量。但每个蓝图实例里存的具体是哪一个选项，是各自独立的。

---

### 一个实际应用的例子（武器系统）

假设你正在做射击游戏：

1. **创建枚举资产：** 在内容浏览器新建枚举 E_WeaponType，添加三个选项：Pistol（手枪）、Rifle（步枪）、Sniper（狙击枪）。
    
2. **在蓝图中使用：**
    
    - 打开你的角色蓝图。
        
    - 新建一个变量 CurrentWeapon，把变量类型选为 E_WeaponType。
        
    - 现在这个变量就是一个下拉菜单。
        
3. **编写逻辑：**
    
    - 拖入 CurrentWeapon 变量，连接一个 **Switch on E_WeaponType** 节点。
        
    - 这个节点会有三个输出引脚：Pistol、Rifle、Sniper。
        
    - 你可以连接不同的逻辑：手枪连“播放手枪音效”，狙击枪连“播放狙击音效”。

# 4.蓝图接口(信号通知)
与事件分发器的区别
![](图片/UE/学习/学习概念/IMG-20260324174142429.png)
### 1. 怎么用？（简易步骤）

使用接口分三步走：**创建 -> 领养（实现） -> 调用**。

#### **第一步：创建接口（定义协议）**

1. 在内容浏览器右键 -> **Blueprints** -> **Blueprint Interface**。
    
2. 命名为 BPI_Interaction（交互接口）。一
    
3. 打开它，在右侧添加一个函数，比如叫 OnInteract（被交互时）。你可以在这里加参数（Inputs），比如“是谁按的E键”。还有输入的参数或者变量

4. 编译，关闭。  
    注意：这里只写函数名字，**不写**具体逻辑。
    

#### **第二步：领养接口（在目标蓝图中实现，谁来继承接口）** 启用接口函数开始事件，然后编写逻辑

假设你有 **门（BP_Door）** 和 **灯（BP_Light）**。

1. 打开 **BP_Door**。
    
2. 点击上方工具栏的 **Class Settings（类设置）**。
    
3. 在右侧细节面板的 **Interfaces** 栏，点击 **Add**，搜索并选中 BPI_Interaction。
    
4. 编译。
    
5. 在左侧 **My Blueprint** 面板的 **Interfaces** 下，==双击== OnInteract（或者右键 -> Implement Function）。
    
6. **写逻辑：** 连线 Timeline 或 Set Rotation 让门打开。
    
7. (同样的步骤去 **BP_Light** 里做一遍，逻辑写成“开关灯”)。
    

#### **第三步：调用接口（在发送者蓝图中）**，传入相关参数，指定目标对象(==必须是领养接口类，或者其子类==)

假设是 **玩家（BP_Character）** 按下 E 键。

1. 使用射线检测（Line Trace）找到前方的物体，得到 Hit Actor。
    
2. 从 Hit Actor 引脚拉出来，搜索 **OnInteract (Message)**。
    
    - **关键点：** 一定要选右上角带有个==**小信封图标**==的那个（Message），不要选普通的函数调用。
        
3. 这就完了。
    

**结果：** 对着门按E，门开了；对着灯按E，灯亮了；对着墙按E，无事发生。

---
### 2.应用场景
蓝图接口在以下场景是**必用**的：

#### **A. 交互系统（Interaction System）**
这是最经典的的用法。

- **场景：** 玩家对着物体按“F”键。
    
- **对象：** 门（开门）、椅子（坐下）、NPC（对话）、武器（捡起）、电梯（按钮）。
    
- **做法：** 统一用接口 BPI_Interact。
    

#### **B. 伤害系统（Damage System）**
- **场景：** 爆炸或子弹击中物体。
    
- **对象：** 敌人（扣血）、玻璃（破碎）、队友（友伤提示）、无敌的墙（冒火花）。
    
- **做法：** 统一用接口 BPI_Damage。
    

#### **C. 物品栏/UI通信**
- **场景：** 你的背包里有把枪，有瓶水，有本书。
    
- **做法：** 当你在UI上点击“使用”时，UI并不知道这个物品是什么类。它只发送一个 UseItem 的接口消息。
    
    - 枪实现了接口 -> 装备。
        
    - 水实现了接口 -> 回血。
        
    - 书实现了接口 -> 显示文本。
        

### 总结
- **普通变量/函数：** 是你自己跟自己说话。
    
- **Cast To（类型转换）：** 是你指名道姓跟某人说话（如果那人不在，你就崩了）。
    
- **蓝图接口：** 是你拿个大喇叭喊话。谁听得懂谁就去做，听不懂的就当没听见。
    

**记住一句话：只要你想让两个毫无关系的蓝图进行互动，首选蓝图接口。**


# 5.音频
## 总结与对比表
导入wav源文件，然后创建Cue，随后给Cue归类，在Cue中绑定Class，统一管理
UE 音频体系的核心是：**Sound Wave（原始音频）→ Sound Cue / MetaSound（逻辑 / 处理）→ Sound Class / Bus（分组混音）→ Audio Component（场景播放）**，从 “素材” 到 “逻辑” 再到 “控制” 和 “场景实例” 逐层向上。

## 一、核心音频资产（最基础）

### 1. Sound Wave（声波 / 原始音频）

- **定义**：导入引擎的**原始音频文件**（WAV/OGG 等），是最底层的音频数据载体。
- **作用**：存储**单段音频波形数据**（如单次脚步声、枪声）。
- **特点**：
    
    - 无逻辑、无分支、无动态变化
    - 仅含基础属性：音量、音调、循环、压缩设置
    
- **类比**：**原材料（一块铁）**

### 2. Sound Cue（声音线索 / 音效逻辑）

- **定义**：**节点图式音频逻辑资产**，用于组合、处理、控制 Sound WaveEpic Games。
- **作用**：
    
    - 拼接多段音频、随机播放、循环、交叉淡化
    - 添加音量 / 音调随机、延迟、混音、衰减
    - 实现**动态音效逻辑**（如走路随机脚步声、环境复合音效）
    
- **特点**：可视化节点编辑、可暴露参数给蓝图 / C++ 控制
- **类比**：**预制件 / 配方（用铁做成弹簧、螺丝）**

### 3. MetaSound（UE5 新一代音频系统）

- **定义**：UE5 替代 Sound Cue 的**高性能 DSP 音频系统**。
- **作用**：
    
    - 完整底层 DSP 控制、模块化音频合成
    - 实时生成、参数自动化、更精准时序控制
    
- **特点**：比 Sound Cue 更强大、更灵活、性能更好
- **类比**：**音频 “材质编辑器”**（可编程、高度自定义）

---

## 二、管理与控制类（分组、混音、全局控制）

### 1. Sound Class（声音类）

- **定义**：**音频分组管理资产**，用于批量控制同类声音Epic Games。
- **作用**：
    
    - 按类型分组：音乐、音效、对话、UI 等
    - 统一控制：音量、音调、滤波器、优先级、并发数
    - 配合 **Sound Mix** 实现**动态混音**（如战斗时压低背景音乐）
    
- **特点**：可分层级（父 / 子类）、全局影响、运行时可动态调整Epic Games
- **类比**：**音频文件夹 + 总控开关**

### 2. Sound Attenuation（声音衰减）

- **定义**：**3D 空间音频规则资产**。
- **作用**：
    
    - 控制**距离衰减**（内半径 / 外半径）
    - 空间化（3D 定位）、空气吸收、遮挡 / 穿透效果Epic Games
    - 混响发送、立体声 / 全景声 pansUnreal Engine 5.6
    
- **特点**：可复用、可被 Sound Cue/Component 引用
- **类比**：**声音在空间中的传播物理规则**

### 3. Sound Concurrency（并发规则）

- **定义**：**控制同时播放数量**的资产。
- **作用**：
    
    - 限制同类型声音最大并发数（如最多 5 个脚步声）
    - 超出时：停止最旧、最低优先级、最远声音
    
- **目的**：防**声音爆音 / 卡顿 / 资源耗尽**

---

## 三、场景播放与实例（运行时）

### Audio Component（音频组件）

- **定义**：**Actor 上的播放组件**，是**场景中真正发声的实例**。
- **作用**：
    
    - 附加到 Actor，在 3D 空间播放 Sound Wave / Sound Cue
    - 运行时控制：播放 / 暂停 / 停止 / 淡入淡出 / 音量 / 音调
    - 承载：衰减、空间混合、循环、优先级
    
- **关系**：
    
    - 可播放 **Sound Wave** 或 **Sound Cue**
    - 属于 **Actor 组件**，有位置、可移动
    
- **类比**：**喇叭 / 音箱**（装在物体上发声）

---

## 四、总线与混音（音频路由）

### 1. Audio Bus / Submix（音频总线 / 子混音）

- **定义**：**信号路由与效果处理节点**。
- **作用**：
    
    - 把多类声音汇总到一条总线（如 “所有环境声”）
    - 统一加效果：混响、EQ、压缩、失真
    - 分层混音结构Epic Games
    
- **特点**：UE5 新音频引擎核心，替代旧 Sound Class 混音

### 2. Sound Mix（声音混合）

- **定义**：**运行时动态混音规则**。
- **作用**：
    
    - 场景 / 状态切换时改变 Sound Class 音量 / 效果
    - 例：菜单→游戏→过场时音乐 / 音效音量变化
    
- **用途**：**音频状态机**

---

## 五、核心概念对比（一眼看懂）

表格

|类型|层级|核心职责|可播放？|动态逻辑|复用性|
|:--|:--|:--|:--|:--|:--|
|**Sound Wave**|素材层|存储原始音频|✅ 直接播|❌ 无|✅ 高|
|**Sound Cue**|逻辑层|组合 / 随机 / 处理音频|✅ 可播|✅ 强|✅ 高|
|**MetaSound**|高级逻辑|DSP 合成 / 生成 / 精准控制|✅ 可播|✅ 极强|✅ 高|
|**Sound Class**|管理层|分组 / 批量控音量 / 优先级|❌ 否|✅ 运行可调|✅ 全局|
|**Attenuation**|空间层|3D 衰减 / 空间 / 遮挡|❌ 否|❌ 静态|✅ 高|
|**Audio Component**|实例层|场景中发声 / 控制|✅ 是实例|✅ 实时控|❌ 场景实例|

---

## 六、一句话总结区别

- **Sound Wave** = **音频文件本身**（素材）
- **Sound Cue / MetaSound** = **音效逻辑 / 处理**（加工）
- **Sound Class / Bus** = **分组混音总控**（管理）
- **Audio Component** = **场景里的喇叭**（播放实例）

**典型工作流**：

导入 WAV → 做成 Sound Wave → 用 Sound Cue 组合逻辑 → 指定 Sound Class 和 Attenuation → 用 Audio Component 在场景播放。

# 9.UI 控制
## (1)基础知识
### 网络复制
**UI 控件永远是“纯本地”的！服务器的 UI 不会复制给客户端，UI 组件本身也不支持网络同步**
**因为 UI 控件（Widget）在虚幻引擎中是**绝对不可通过网络复制的**，它连网络通道都没有。UI 事件只能在本地电脑上自己调用自己。
**“网络传数据，本地驱动 UI”**。
#### 第一步：在“血条 UI 蓝图”里准备一个更新事件

首先，我们需要让血条 UI 拥有一个接收数据的“接口”。

1. 打开你制作进度条的那个 **UI Widget 蓝图**（就是带有 ProgressBar 进度条的那个蓝图）。
    
2. 进入事件图表（Event Graph）。
    
3. 新建一个自定义事件（Custom Event），命名为 **UpdateHealthBar（更新血条）**。
    
4. 给这个事件添加一个 **Float（浮点型）输入参数**，命名为 Percent（百分比）。
    
5. 把这个参数连到你的 ProgressBar（进度条）的 **Set Percent（设置百分比）** 节点上。
    

(这一步的意思是：只要有人调用这个事件并传个数字进来，进度条就会变。)


#### 第二步：确保小怪的血量使用了 RepNotify

(如果你之前已经按照我说的做过，这一步可以检查一下)

1. 打开**小怪蓝图（NPC Character）**。
    
2. 找到表示当前血量的变量 CurrentHealth。
    
3. 在右侧细节面板，把 **复制（Replication）** 设置为 **RepNotify**。
    
4. 此时左侧会自动生成一个名叫 **OnRep_CurrentHealth** 的函数。
    
#### 第三步：在 OnRep 函数中刷新头顶的 UI（最核心的一步！）

这也是新手最容易卡住的地方：怎么在小怪蓝图里拿到它头顶那个 UI 并更新它？

双击打开小怪蓝图里的 **OnRep_CurrentHealth** 函数，按顺序连线：

1. **拖出控件组件：** 从左侧组件列表里，把小怪头上的那个 **Widget（控件组件）** 拖到图表里。
    
2. **获取 UI 对象：** 从这个 Widget 组件拉出线，搜索并调用 **Get User Widget Object（获取用户控件对象）**。  
    (注意：控件组件只是一个 3D 的框，里面的 Object 才是你真正的 UI 蓝图)。
    
3. **类型转换（Cast）：** 从上面那个节点的返回值拉出线，使用 **Cast To 你的血条UI蓝图名字**（比如 Cast to WBP_HealthBar）。
    
4. **调用更新：** 从转换成功的蓝色引脚拉出线，搜索你刚才在第一步建的事件：**UpdateHealthBar**。
    
5. **计算百分比传进去：** 把小怪当前的 CurrentHealth 除以 MaxHealth（当前血量 / 最大血量），得出一个 0~1 之间的小数，连入 Percent 引脚中。


### 💡 运行逻辑大白话（为什么这样就不出 Bug 了）：

1. **服务器（建主机的玩家）：** 挥刀砍小怪 -> 触发扣血逻辑 -> 修改了小怪的 CurrentHealth。
    
2. **网络底层自动工作：** 服务器发现 CurrentHealth 变了，且它是 RepNotify。于是立刻通过网线，把最新的血量发给所有客户端。
    
3. **客户端（其他玩家的电脑）：** 收到新的血量 -> **自动触发 OnRep_CurrentHealth 函数！**
    
4. **客户端执行刷新：** 客户端在这个函数里，找到了自己电脑上生成的小怪头上那个 3D Widget 框 -> 掏出里面的 UI -> 把最新的血量算成百分比塞给进度条 -> **血条成功下降！**
    

**⚠️ 附加避坑指南：**  
很多新手喜欢在 UI 的进度条上直接用 **“绑定（Bind）”** 功能，然后在里面写 Cast 去强行读取小怪的血量。  
**在联机游戏中，强烈建议不要用 Bind！**  
因为 Bind 是每帧（Tick）都在执行的，不仅极大地消耗性能，而且在客户端还没完全加载好小怪的时候，极容易报空指针（Accessed None）错误。用上面教你的 **“事件驱动（OnRep 触发刷新）”** 才是最正规、最省性能的联机 UI 做法！

##### 1. 选定键时 (On Key Selected) —— **负责底层逻辑（改键结果）**

这就是你上一张截图里正在用的事件。

- **触发时机：** 当玩家点开了这个框，并且**真真切切地按下了某一个具体的键**（比如按下了 F 键），输入被成功捕获的那一瞬间触发。
    
- **附带数据：** 它会把玩家刚才按下的那个键（Selected Key）传出来。
    
- **核心作用：** 专门用来做**“保存与应用”**。在这里执行 Map Player Key 把新按键写入底层系统。
    
- **大白话：** “报告！玩家选好新按键了，是 F 键！”
    

---

##### 2. 选择键已变更时 (On Is Selecting Key Changed) —— **负责表面表现（UI 状态）**

这个事件的全称其实是“正在选择键的**状态**已变更时”。

- **触发时机：** 只要这个控件的“监听状态”发生切换，它就会触发。**它会触发两次**：
    
    1. **第一次：** 玩家**刚点击**这个框，它变成“等待输入...”状态时（此时传出的布尔值为 True）。
        
    2. **第二次：** 玩家按完键了，或者按了 Esc 取消了，它退出“等待输入”状态，变回正常显示时（此时传出的布尔值为 False）。
        
- **附带数据：** 它不传具体按了什么键，只传一个**布尔值 (Boolean)**，告诉你“现在是不是正在等玩家按键”。
    
- **核心作用：** 专门用来做**“UI 动画与防误触”**。
    

---

### 💡 3A 级实战：它们怎么配合使用？

在《黑神话：悟空》这种级别的 UI 里，只用第一个事件是不够的。第二个事件才是提升质感的关键：

**场景还原：**

1. 玩家点击了“向前移动”的按键框。
    
2. 触发 **[选择键已变更时] (True)**：
    
    - 你在这里写逻辑：让主菜单周围的区域变暗，或者禁用其他所有的按钮（防止玩家在改键的时候乱点到别的设置上）。
        
3. 玩家按下 W 键。
    
4. 触发 **[选定键时]**：
    
    - 拿着 W 键去底层执行改绑、覆盖旧键位、保存设置。
        
5. 紧接着自动触发 **[选择键已变更时] (False)**：
    
    - 你在这里写逻辑：恢复周围界面的亮度，重新启用其他按钮的点击功能。
        

**总结：**

- **选定键时：** 拿来改底层数据。
    
- **选择键已变更时：** 拿来做界面动画、禁用/启用其他 UI。

#### 1. 选择已变化时 (On Selection Changed) —— **最常用**

这是最重要的事件。当玩家点击下拉框并选择了一个不同的选项（比如从“窗口模式”切到了“全屏模式”）时，这个事件就会触发。

- **参数含义：**
    
    - **Selected Item (字符串):** 玩家刚刚选中的文本内容（例如 "GBT2706"）。
        
    - **Selection Type (枚举):** 告诉你是怎么选中的（是玩家手动点选的，还是程序代码自动设定的）。
        
- **实际案例：**  
    在这里写逻辑：如果选中的是“全屏”，就执行 Set Fullscreen Mode 指令。

#### 2. 打开时 (On Opening)

当玩家点击下拉框，**下拉列表弹出来的那一瞬间**触发。

- **用法：** 点击 **“+”** 号生成事件。
    
- **使用场景：**
    
    - **动态刷新：** 比如你是一个“显示器输出”的选择框。你可以在这个事件里写逻辑，先 Clear Options（清空选项），然后重新获取电脑当前连接了几个显示器，再把最新的名字 Add Option 进去。这样能保证玩家打开菜单时看到的是最实时的数据。
        
    - **播放音效：** 点击下拉框时播放一个“咔哒”的 UI 打开声音。

#### 3. 生成控件事件时 (On Generate Widget Event) —— **进阶用法**

这个和上面两个不一样，它左边是一个“链接/绑定”图标，而不是“+”号。它用于**自定义下拉列表里每一行的长相**。

# 13.子类蓝图与父类
![](图片/UE/学习/学习概念/IMG-20260301171509036.png)
**它就是蓝图版的 Super::BeginPlay();**。

还记得你刚才在 C++ 代码里写的这一行吗？

```cpp
void AMy_Player::BeginPlay()
{
    Super::BeginPlay(); // <--- 就是这一行！
    // ...
}
```

**“将调用添加到父函数” (Add call to parent function)** 的作用完全一样。

### 详细解释

#### 1. 为什么要用它？（继承的逻辑）

在虚幻引擎中，类是**分层级**的（父类 -> 子类）。

- **父类（比如你的 C++ 类 AMy_Player）**：在 BeginPlay 里写了“设置初始血量为 100”。
    
- **子类（比如基于这个 C++ 创建的蓝图 BP_MyPlayer）**：你想在 BeginPlay 里加一个“播放出生特效”。
    

如果你在蓝图里直接拉一个 Event BeginPlay 节点并连上“播放特效”，引擎默认会认为：**“哦，你想完全重写（Override）父类的逻辑。那你父类里写的‘设置血量’我就不执行了，只执行你的‘播放特效’。”**

后果就是：特效播放了，但血量是 0（因为父类代码没跑），角色直接死了。

#### 2. 这个按钮的作用

当你点击“将调用添加到父函数”后，蓝图里会多出一个橙色的节点（通常叫 Parent: BeginPlay）。

你应该把它连在你的逻辑**最前面**（或者最后面，看需求）：

 **[事件开始播放]** ---> **[父：开始播放]** ---> **[播放特效]**

这样执行顺序就变成了：

1. 先去执行父类（C++）里的代码（设置血量）。
    
2. 再回来执行子类（蓝图）里的代码（播放特效）。
    

### 什么时候必须用？

- **几乎总是需要！**
    
- 特别是在 **BeginPlay**（开始游戏）、**Tick**（每帧更新）、**OnPossess**（控制角色）这些核心事件上。
    
- 因为虚幻引擎底层的 Actor 或 Character 类在这些函数里做了很多你看不见的初始化工作（比如初始化移动组件、物理模拟等）。如果你把父函数调用删了，你的角色可能动不了，或者直接卡死。
    

### 总结

- **在 C++ 里**：你手写 Super::函数名(); 来保留父类功能。
    
- **在蓝图里**：你右键点击“将调用添加到父函数”来保留父类功能。
    

**如果你发现你的蓝图角色有些奇怪的 Bug（比如血量不对、移动不了），第一件事就是检查：是不是重写了某个事件，但忘记连上这个橙色的“父函数”节点了。**

## 修改输入
![](图片/UE/学习/学习概念/IMG-20260415210108512.png)
### 1. 它是怎么知道绑定在哪个“输入操作”上的？

关键全在截图里的那个 **Mapping Name** 变量引脚上！

- **旧系统的痛点：** 以前你告诉系统“我要改 IA_Move（移动）”，系统会懵掉，因为 IA_Move 里面包含了 W、A、S、D 四个键，它不知道你要改哪个方向。
    
- **新系统的精准制导：**  
    你在配置 **IMC (Input Mapping Context)** 时，点开 W 键的高级设置，勾选 Player Mappable Options 后，里面有一个 **Name** 字段。假设你给 W 键起的 Name 叫 **MoveForward**。
    
- **对应关系：**  
    当你在这个蓝图节点里，把 Mapping Name 变量的值设为 MoveForward 时，系统就会去底层翻找：“哪个操作里面包含一个名字叫 MoveForward 的可映射选项？” 找到后，它自然就知道这对应的是 IA_Move 操作里的“向前”动作。
    

### 2. 它是怎么知道绑定在哪个“键位槽”上的？

注意看你截图里 Make MapPlayerKeyArgs 节点中的第二个参数：**Slot (槽)**，你当前选的是 **第一个 (First)**。

这是什么意思呢？

- 在 3A 游戏中，一个动作通常可以有两个快捷键。比如“跳跃”可以是键盘的 Space，同时也可以是鼠标的 侧键。
    
- 这个 Slot 就是用来决定你要覆盖哪一个的：
    
    - **第一个 (First)：** 覆盖它的主键（Primary Key）。把你新按下的键替换掉原本的 Space。
        
    - **第二个 (Second/Third/etc)：** 覆盖它的备用键。
        
- 如果你勾选了下面的 Create Matching Slot If Needed，如果原本这个动作只有一个主键，你指定要改“第二个”槽位，引擎会自动帮你创建一个备用键槽位并绑上去。
    

### 3. 完整的连线逻辑复盘

把你的截图翻译成大白话，引擎执行的逻辑是这样的：

> **“系统大管家（User Settings），玩家刚才按下了 Selected Key（比如 F 键）。请你去设置里找一个叫作 Mapping Name（比如 MoveForward）的条目，把它的 第一个槽位（主键）强行替换成这个 F 键。”**

### 💡 留给你的下一步操作（最容易出错的地方）：

因为你现在做的是动态生成的按键列表（循环生成了很多行子控件），你需要确保：

在生成每一行 WBP_KeybindRow 子控件时，必须把你从数据表或系统里读出来的那个真实的 **Mapping Name**，赋值给当前这一行的这个 Mapping Name 变量。

在虚幻引擎中，这对应的是底层的网络协议选择（类似 TCP 和 UDP 的区别）。

### 1. 可靠函数 (Reliable) —— “挂号信”

当你勾选了“可靠函数”：

- **保证送达：** 如果网络波动导致这个数据包丢了，引擎会自动重新发送，直到对方收到为止。
    
- **保证顺序：** 如果你先后发送了事件A和事件B，对方一定会先处理A再处理B。
    
- **代价：** 它会消耗更多的带宽和 CPU 性能。如果网络很差，大量的可靠函数会导致网络阻塞（像堵车一样），甚至导致玩家掉线。
    
- **适用场景：** **绝对不能丢的关键逻辑。**
    
    - **死亡（Death）：** 角色死了必须让所有人都知道，不然会导致“无敌外挂”或者客户端表现不同步。
        
    - **扣钱/买东西：** 涉及数值和重要状态切换的操作。
        
    - **聊天信息：** 发出去的话不能平白无故消失。
        

### 2. 不可靠函数 (Unreliable) —— “传单”

如果你不勾选“可靠函数”：

- **不保证送达：** 发出去就管了。如果网络刚好在那一秒抖动了一下，这个包丢了，对方就永远收不到了，引擎也不会重发。
    
- **不保证顺序：** 后发的包可能会先到。
    
- **优势：** 速度极快，对网络负担小。
    
- **适用场景：** **丢一两次也没关系的视觉/瞬时效果。**
    
    - **特效/音效：** 比如受击火花、脚步声。如果因为网络卡顿丢了一个火花特效，玩家几乎察觉不到，没必要为了一个火花去占用宝贵的带宽。

# 16.骨骼动画
## 第一座山：IK Rig（IK 绑定）—— “给骨骼贴标签”

**【概念本质】**：UE引擎非常笨，它不知道你导入的模型哪部分是手、哪部分是腿。IK Rig 的作用，就是让你在骨骼上“画线贴标签”，教引擎认识这个身体。你需要为**源模型**和**目标模型**各建一个 IK Rig。

### 第一步：设置重定向根 (Retarget Root)

- **在哪操作：** 左侧面板【层级 (Hierarchy)】-> 找到骨骼树里的盆骨（通常叫 Pelvis、Hips 或 Spine_00）。
    
- **怎么操作：** 右键点击盆骨 -> 选择 **设置重定向根 (Set Retarget Root)**。
    
- **干什么用的：** 决定角色在世界空间的“中心”。
    
    - 如果不设，角色的骨盆将被死死锁在坐标轴原点（也就是掉在地上）。
        
    - 设了之后，源角色往前跑3米，目标角色也会根据体型比例往前跑相应的距离。
        

### 第二步：绑骨骼链 (Retarget Chains) —— “画绿线”

- **在哪操作：** 依然在左侧【层级】的骨骼树里。
    
- **怎么绑（极其重要，千万别选错）：**
    
    1. **左臂：** 左键单击 UpperArm_L（大臂），按住 Shift 键，左键单击 Hand_L（手腕）。此时大臂到手腕中间的骨骼会变蓝。
        
    2. **建链：** 右键点击变蓝的区域 -> 选择 **从选定骨骼新建重定向链 (New Retarget Chain from Selected Bones)**。
        
    3. **命名：** 弹出的窗口一定要规范命名，比如 LeftArm。（如果源角色叫 LeftArm，你的新角色也必须叫 LeftArm，大小写无所谓，但单词要一致）。
        
- **干什么用的：** 告诉引擎“这是一条可以活动的胳膊”。只有画了绿线的地方，动作数据才能传导过去。
    
- **需要绑哪些基础链？**
	- 设置骨盆
		
    - Spine (脊柱：从脊柱第1节选到胸颈交界处)

	- 
    - LeftArm / RightArm (手臂：大臂选到手腕，**绝对不要把手指包含进去！**)
        
    - LeftLeg / RightLeg (腿部：大腿选到脚踝)
        
    - Head (头部：脖子选到头顶)
        
    - （可选）每根手指单独建链：大拇指建一条、食指建一条...
        

### 第三步：添加解算器和 IK 目标 (Solvers & Goals) —— “做手柄”

(注：如果只是简单的动作，这一步可以跳过。但如果需要精准交互、防滑步，这一步必做)

- **在哪操作：** 界面左下角的【解算器堆栈 (Solver Stack)】和主视口。
    
- **怎么操作：**
    
    1. 点击左下角 **+ 新增解算器** -> 选择 **全身体IK (Full Body IK)**。
        
    2. 在左侧【层级】里，选中 Hand_L，右键 -> **新建 IK 目标 (New IK Goal)**。给四肢末端（双手、双脚）都建上。此时视口里会出现橙色方块。
        
    3. 把解算器和目标连起来：在左下角刚建好的【全身体IK】条目上 **右键** -> **添加设置目标** -> 把你建的双手双脚IK选进去。
        
- **干什么用的：** 动作传导过去后，如果手的位置稍微有点偏差，IK 解算器会强行拉住那个橙色方块对准位置，并自动调整肘部的弯曲度，保证动作完美。

## 第二座山：IK Retargeter（IK 重定向器）—— “动作翻译机”

**【概念本质】**：源角色和目标角色的骨架长得不一样，初始姿势也不一样（一个是 T-Pose，一个是 A-Pose）。重定向器就是让它们俩互相认识，对齐姿势，然后把左边的动作拷贝给右边。

### 第一步：分配资产与基本排版

- **在哪操作：** 右侧【细节 (Details)】面板。
    
- **怎么操作：**
    
    1. **Source IKRig Asset (源)：** 选官方小白人的 IK Rig（提供动作的人）。
        
    2. **Target IKRig Asset (目标)：** 选你自己刚才建的那个 IK Rig（接收动作的人）。
        
    3. **目标网格体偏移 (Target Mesh Offset)：** 把 X 轴的数值改大（比如改成 150）。
        
- **干什么用的：** 让两个小人不要重叠在原点，把它们拉开并排站着，方便你对比检查。
    

### 第二步：链映射 (Chain Mapping) —— “翻译对暗号”

- **在哪操作：** 右下方的【链映射】选项卡。
    
- **怎么操作：** 检查列表。左边一列是 Source 的链，右边是 Target 的链。
    
    - 如果引擎没自动对上（比如右边显示 None），你就点击下拉菜单，手动把 LeftArm 对接给 LeftArm。
        
- **干什么用的：** 建立数据传输通道。如果有任何部位显示未映射，输出日志就会报黄色警告，那个部位重定向后就不会动。
    

### 第三步：调 Pose（对齐起跑线）—— 👑 整个流程最关键的一步！

- **【痛点解析】**：如果官方小白人是 A-Pose（手半垂着），你的模型是 T-Pose（手平举）。如果你不调 Pose 直接重定向，引擎会以为“平举”就是你的“半垂状态”。结果重定向出来的动画，你的模型手臂会永远往上翘45度，甚至插进脑袋里！
    
- **在哪操作：** 左侧面板上方的 **当前重定向姿势 (Current Retarget Pose)**。
    
- **怎么建/怎么调：**
    
    1. 点击【当前重定向姿势】旁边的 **创建 (Create)** 按钮 -> **新建 (Create New)** -> 命名为 Matched_Pose。
        
    2. 点击旁边的 **编辑模式 (Edit Mode)** 按钮（此时整个背景变暗，进入编辑状态）。
        
    3. **在主视口中：** 直接点击你的目标模型（右边那个）的骨骼点（比如肩膀、大臂）。
        
    4. 按键盘 **E** 键调出旋转工具。
        
    5. 小心地旋转目标模型的肩膀、大臂、小臂、大腿，让它的姿势看起来和左边的小白人 **完 全 一 模 一 样**。
        
    6. 重点检查：手臂下垂的角度、脊柱的倾斜度、膝盖是否弯曲。
        
    7. 调完后，再次点击 **编辑模式** 按钮退出保存。
        
- **干什么用的：** 统一初始变量，彻底消除肩膀扭曲、腋下穿模的问题。
    

### 第四步：根骨骼属性微调 (Root Settings)

- **在哪操作：** 左侧选中 Pelvis 所在的链（通常叫 Root），看右侧【细节】面板。
    
- **怎么操作：** 找到 **平移模式 (Translation Mode)**。
    
    - 默认是 None。
        
    - 改为 **Globally Scaled (全局缩放)**。
        
- **干什么用的：** 如果你的模型是个 1 米高的侏儒，小白人是 1.8 米的成年人。如果不调，侏儒跳跃时会直接飞到 1.8 米的高度。选了全局缩放，引擎会根据体型比例，让侏儒只跳 1 米高，动作看起来更协调。
    

### 第五步：预览与导出动画

- **在哪操作：** 右下角【资产浏览器 (Asset Browser)】。
    
- **怎么操作：**
    
    1. 里面列出了源模型的所有动画。双击任意一个（比如跑步）。
        
    2. 此时两个模型应该会同步跑起来。你可以拖动下方的进度条，或者旋转视角360度观察。
        
    3. 如果没问题，选中你想要的动画，点击窗口上方的 **导出选定动画 (Export Selected Animations)**，选择一个你的项目文件夹。
        
    4. 完成！现在你的新模型有了专属的动画文件，可以直接拿到蓝图里用了。

# C++指针
## 罗列
![](图片/UE/学习/学习概念/IMG-20260608151223578.png)
- 实际区别
```cpp
TWeakObjectPtr vs TObjectPtr

  UPROPERTY() TObjectPtr<UObject> StrongRef;   // 阻止对象被GC回收
  TWeakObjectPtr<UObject> WeakRef;             // 不阻止回收，可检查是否失效

  // WeakObjectPtr 用法：
  if (WeakRef.IsValid())          // 先检查是否还在
  {
      WeakRef->SomeFunction();
  }

  TSoftObjectPtr — 延迟加载

  // 只存路径，不加载到内存
  UPROPERTY() TSoftObjectPtr<UTexture2D> IconTexture;

  // 需要用的时候才加载
  if (IconTexture.IsPending())    // 还没加载
  {
      IconTexture.LoadSynchronous();  // 同步加载（或使用异步加载）
  }

  非 UObject 的智能指针

  // 你项目里的 Puerts JS 环境就是用 TSharedPtr
  TSharedPtr<puerts::FJsEnv> JsEnv;  // 共享所有权
  TUniquePtr<SomeClass> Unique;      // 独占所有权，不能复制

```

## 使用时机
###  1. 先看它是 UObject 还是普通 C++ 对象                                 

  UObject 及其子类（Actor、Component、Asset 等）→ 必须用指针

  // ✅ 正确：UObject 不能被 new 在栈上，只能用指针 + UPROPERTY
```cpp
 UPROPERTY() TObjectPtr<UAbilitySystemComponent> ASC;
```

  // ❌ 错误：UObject 不能这样声明
```cpp
  UAbilitySystemComponent ASC;  // 编译都过不了
```

  因为 UObject 的构造/析构完全由引擎的 GC 系统管理，你不能在栈上创建它。

  普通 C++ 结构体/类 → 视情况而定

  // ✅ 可以用值，直接内嵌
```cpp 
 FVector Location;
FRotator Rotation;
int32 Health;
```

  // ⚠️ 如果比较大或者需要共享，也可以用指针
```cpp
  TSharedPtr<FBigData> BigData;
```

### 8. 快速决策表
```text
问：这个成员是 UObject 的子类吗？
    ├─ 是 → 必须用 TObjectPtr\<T> / T* + UPROPERTY
    └─ 否 → 问：它的生命周期与我完全同步吗？
             ├─ 是 → 问：是多态场景吗（父类存子类）？
             │        ├─ 是 → 用 TUniquePtr / 裸指针
             │        └─ 否 → 问：可能为 null 吗？
             │                 ├─ 可能 → 用 TOptional<T> 或指针
             │                 └─ 不可能 → 直接用值 T
             └─ 否 → 它的所有者是谁？
                      ├─ 外部传入，不拥有 → 裸指针
                      ├─ 多个对象共享 → TSharedPtr
                      └─ 本对象独占且不是 UObject → TUniquePtr

```  
  一句话原则:
能用值就用值，需要用指针的时候你通常能明确说出理由（UObject、可为 null、多态、共享生命周期）。

# 资源加载与打包
==**优先方案B的路线2**==
## 方案 A：少量核心资源（必须保留引用，走 LFS）

项目必不可少的贴图、模型，蓝图大量依赖，删掉就红引用。

- 这类**不能拿掉**，只能用 LFS 托管，控制总量，不要塞 GB 级原始素材。
- 只提交工程内正在使用的精简资源，原始高清源文件（PSD、MAX 工程）不要放进仓库。

## 方案 B：大量可选 / 超大素材（移出 Git，解决红引用有两条路线）

> 适合素材几十 GB，LFS 额度扛不住

### 路线 1：外部资源下载 + 本地目录对齐（推荐）

1. 源码仓库（Git）只存代码、蓝图、配置，**不带大素材**
2. 在 README 写清楚：使用者下载源码后，**把素材解压到指定文件夹路径**
3. 保证解压后的目录结构和你本机完全一致
    
    ✅优点：蓝图引用不会变红；
    
    ⚠缺点：使用者需要手动下载并放到正确位置，路径不能错。

> 举个 UE 例子：
> 
> 蓝图引用 `Content/AssetPack/tree.uasset`
> 
> 仓库不包含`AssetPack`文件夹，使用者自行下载资源包解压到`Content/`下，路径对上，引用正常。

### 路线 2：==运行时动态加载==，放弃编辑器直接引用（适合大型 MMO / 开放世界项目）

#### 不在蓝图编辑器里拖入资源建立静态引用。

- 编辑器不硬绑定资源；
- C++/ 蓝图代码通过字符串路径**运行时动态加载资源**；
	- 
- 资源独立打包，作为外部 Pak 文件，单独分发。
    
    ✅优点：仓库彻底摆脱大资源，不存在编辑器红色丢失引用；
    
    ⚠缺点：不能在编辑器里直观预览，开发流程更复杂，小项目没必要。
#### 具体实现思路 
1. **纯动态字符串加载，编辑器里蓝图预览不到资源，会显示丢失引用红色标记，但是打包运行正常！**
2. UE 中动态加载有两套：==**AsyncLoad==（异步加载，推荐，不卡帧）** / LoadObject（同步加载，会卡顿，尽量少用）
3. 资源路径格式（两种写法）
    
    - 编辑器路径：`/Game/Map/TestMap.TestMap`（蓝图代码里用这个）
    - 磁盘路径不能直接用！不能填 Windows 文件路径
4. 优点
	不会阻塞游戏主线程，适合游戏运行时按需加载模型、贴图。
5. 缺点
	编辑器预览失效，只有**运行时**才能加载成功。

> 前提：资源**不要在蓝图面板拖拽引用**，否则变成静态依赖，资源依然被打包进主 pak。
> 
> 如果你想资源脱离主工程 pak 单独分发，要用到**Pak 文件 + Mount**，单纯字符串加载做不到外置资源。
## 方案 C：不要把所有素材一锅丢进仓库（避坑重点）

很多人踩坑：

把全部原始素材、导出缓存、高分辨率源文件全部提交 Git，LFS 瞬间爆满。

区分两类文件：

1. **工程内 uasset（游戏运行要用、蓝图依赖）**：要么 LFS，要么外部 Pak 分发
2. **外部原始源文件：psd、blend、max、拍摄原图**：**永远不要放进 Git**，单独网盘保存。

## 最简取舍总结

1. 小项目、资源不多：必要 uasset 用 LFS，原始素材网盘存放。
2. 大资源很多、LFS 不够用：源码单独 Git，素材做成独立资源包，告诉使用者解压到**完全相同目录**，引用正常不报错。
3. 如果不想让用户手动放资源：只能接受 LFS，或者使用 Release 附件分发完整工程压缩包（适合阶段性交付，不适合日常迭代）。

## image（图片）与Brorder（边界）的区别
### 1. 容器属性（能不能装东西）

这是最大的区别。

- **图像 (Image)：** 它是一个**叶子控件**。它不能包含任何子控件。你不能把文字或按钮放进 Image 里面。
    
- **边界 (Border)：** 它是一个**容器控件**。它可以包含**一个**子控件（通常我们会在里面放水平框或垂直框）。
    
    - **3A 用法：** 就像你之前做的设置行，我们把整行逻辑放进一个 Border 里。这样 Border 既提供了背景图，又包裹住了里面的文字和组合框。
        

---

### 2. 前景颜色继承 (Foreground Color) —— **你的救星**

这是我之前极力推荐你用 Border 的原因。

- **图像 (Image)：** 没有“前景颜色”概念。你改它的颜色，只会影响图片本身。
    
- **边界 (Border)：** 拥有 **Foreground Color (前景颜色)** 属性。
    
    - **黑科技：** 如果 Border 里面的子控件（如文本、组合框）勾选了 **“继承 (Inherit)”**，当你通过蓝图修改 **Border 的前景颜色**时，里面所有的字会**同时变色**。
        
    - **Image 做不到这一点**，如果你用 Image 做背景，你得一个一个去改里面文字的颜色。
        

---

### 3. 内容填充 (Padding)

- **图像 (Image)：** 只有自己的边距。
    
- **边界 (Border)：** 拥有 **Content Padding (内容填充)**。
    
    - 你可以通过设置 Border 的 Padding，轻松控制里面的文字距离边缘有多远，而不需要额外加“间隔区（Spacer）”。
        

---

### 4. 命中测试与交互 (Hit Testing)

- **图像 (Image)：** 虽然也能检测鼠标，但通常只用于装饰。
    
- **边界 (Border)：** 是处理“整行点击”、“整行悬停”的最佳选择。
    
    - 因为它是一个容器，无论鼠标点在里面的文字上、间隙上，还是背景上，只要鼠标在 Border 的矩形范围内，Border 都能稳定地捕捉到事件。
        
    - 如果你用 Image 做背景，文字浮在上面，鼠标在文字和背景之间移动时，经常会发生事件抖动。
        

---

### 5. 性能与用途

- **图像 (Image)：** 极其轻量。如果你只需要在旁边放个图标（比如按键图标），用 Image。
    
- **边界 (Border)：** 稍微重一点点（因为它要计算子控件布局）。如果你需要一个**有背景、能点击、且里面的内容需要同步变色**的区域（比如设置菜单的每一行），必须用 Border。
    

---

### 💡 总结你的选择：

- **什么时候用 Image？**
    
    - 做左侧那一排圆形图标按钮时。
        
    - 做键盘映射页里每一个独立的按键底图时。
        
    - 做装饰用的分割线、水墨纹理时。
        
- **什么时候用 Border？**
    
    - **设置项的整行背景：** 方便实现“点击整行高亮，且文字同步变色”。
        
    - **侧边栏的感应区：** 方便实现“鼠标进入这一块区域就弹出抽屉”。
        
    - **提示框的底盒：** 方便给文字加背景和边距。

## 标签，枚举，变量
标签GameplayTags==简洁，高效，可叠加==
如果说传统的编程是靠“变量”来判断状态，那么现代虚幻引擎开发（特别是你正在学的 **GAS 插件**）则是靠“标签”来驱动逻辑。

### 1. 它解决了什么痛点？

在没有 GameplayTags 之前，我们要判断一个玩家的状态，通常会写大量的布尔值（bool）或枚举（Enum）：

- bool bIsStunned; (是否被晕眩)
    
- bool bIsCrouching; (是否在蹲下)
    
- bool bCanAttack; (是否能攻击)
    

**痛点：** 当状态变多时，逻辑会变得极其混乱。比如：“如果玩家在晕眩状态，就不能切换到蹲下状态”。你需要写无数个 if (bIsStunned && !bIsCrouching)。

### 2. GameplayTags 是怎么做的？

它把状态变成了一个个**分层级的名字**，比如：

- State.Buff.SpeedUp (加速状态)
    
- State.Debuff.Stun (晕眩状态)
    
- Ability.Skill.Fireball (正在释放火球术)
    

**核心优势：**

- **层级化：** 你可以查询一个对象是否有 State.Debuff 标签。如果它有 State.Debuff.Stun，那么查询父级标签 State.Debuff 也会返回 True。
    
- **性能极高：** 虽然看起来是字符串，但 UE 在底层把它们转换成了数字索引（FName/Hash），判断速度极快。
    
- **数据驱动：** 你可以在编辑器里直接下拉勾选标签，不需要去代码里改变量名。
    

---

### 3. GameplayTags 在你的 GAS (Gameplay Ability System) 项目中起什么作用？

既然你在做 Warrior_GAS，GameplayTags 就是 GAS 的**灵魂**。在 GAS 中，它有三个核心用途：

#### A. 状态描述 (State Representation)

GAS 不会用 bIsDead 这种变量，它会给 Actor 加上一个 State.Dead 标签。

- UI 系统监测到这个标签，就弹出死亡界面。
    
- 动作系统监测到这个标签，就播放死亡动画。
    

#### B. 技能限制 (Ability Requirements)

你可以设置一个技能：

- **Ability Tags**: 该技能的标签（如 Ability.Attack.Melee）。
    
- **Cancel Abilities with Tag**: 释放该技能时，取消所有带 Ability.Stealth（潜行）标签的技能。
    
- **Activation Blocked Tags**: 如果玩家身上带有 State.Stun（晕眩）标签，则禁止释放该技能。
    

#### C. 标签过滤 (Tag Queries)

你可以写非常复杂的逻辑判断，例如：

- “如果目标拥有 Enemy.Boss 且 **没有** State.Immune.Debuff 标签，则对其施加伤害。”
    

---

### 4. 为什么不用枚举 (Enum)？

- **枚举是互斥的**：一个变量同一时间通常只能是一个枚举值（比如只能是“走”或者“跑”）。
    
- **标签是并行的**：一个 Actor 同一时间可以拥有成百上千个标签。你可以既是 State.Poisoned（中毒），又是 State.Stunned（晕眩），还是 Team.Blue（蓝队）。
